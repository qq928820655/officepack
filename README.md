# officepack — 任意文件 ⇄ 纯文本 无损装换

把**任意文件**（`doc/docx/xls/xlsx/ppt/pptx`、`pdf`、`zip/rar/7z`、`md/java/sql/py` 源码、
图片、音视频……）打包成一段**纯文本**，之后用这段文本 **100% 还原**出原文件 ——
还原后 SHA-256 与原文件逐字节一致。

```
报表.docx ──打包──> 报表.docx.base91.opk.txt  （纯 ASCII 文本，可加密）
报表.docx.base91.opk.txt ──还原──> 报表.docx   （SHA-256 完全一致）
```

> **不想自己构建？** 直接下打包好的 exe：
> [**Releases（最新版）**](https://github.com/qq928820655/officepack/releases/latest)
> —— 图形界面版（推荐）、单文件便携版、命令行版、应急修复包。

## 支持哪些文件

**结论：任意文件都能装。** 底层走的是「原始字节 → 压缩 → 加密 → 编码」，
不解析文件内容，所以只要求「能读出来」，不要求「认得这个格式」。

| 类别 | 扩展名 | 预览 |
|---|---|---|
| Office（OOXML） | `docx/docm/xlsx/xlsm/pptx/pptm` | 抽正文 |
| Office（老二进制） | `doc/xls/ppt/msg` | 扫可打印串 |
| PDF | `pdf` | 解 FlateDecode 流抽字符串 |
| 压缩包 | `zip/jar/apk/war/whl/odt/epub…` | 列目录 + 条目数 |
| 压缩包（无标准库） | `rar/7z/tar/gz/xz` | 仅类型标注 |
| 源码 / 文本 | `md/java/sql/py/js/ts/go/rs/json/xml/yaml/ini/log…` | 按 UTF-8 → GBK 解码 |
| 图片 | `png/jpg/bmp/gif/webp/tif` | 格式 + 像素尺寸 |
| 音视频 / 可执行 / 未知 | `mp3/mp4/exe/dll/…`、任意扩展名 | 无（不影响还原） |

预览只是**给人看的注释**，抽不出来（例如 `rar`、`mp4`）也完全不影响无损还原。

## 为什么不是「提取文字再还原」

Word 二进制（OLE2）和 docx（ZIP+XML）里包含样式表、压缩流、字体嵌入、修订记录、图片。
**把正文抽成纯文本后，这些信息永久丢失，无法还原成原文件。**

所以本工具采用「编码载体」路线：

```
原始字节 → 压缩 → 加密 → 编码成可打印 ASCII → 文本
文本 → 解码 → 解密 → 解压 → 原始字节（SHA-256 校验）
```

正文预览只是**附赠给人看的注释**，不参与还原。

## 快速开始

**免安装，双击即用**（目标机器不需要装 Python，Windows 10/11 64 位）：

| 产物 | 启动速度 | 说明 |
|---|---|---|
| `dist\OfficePack-GUI\OfficePack-GUI.exe` | **1~3 秒** | 图形界面，支持拖拽，**推荐**（从同目录 `启动.bat` 进，会先自检） |
| `dist\OfficePack-GUI-win64.zip` | — | 整个 GUI 目录的压缩包，**换电脑时传这个** |
| `dist\officepack\officepack.exe` | **0.5 秒** | 命令行版 |
| `dist\OfficePack-GUI-便携单文件（启动慢）.exe` | 45 秒 | 只有这一个文件，拷走即用；功能与目录版一致 |
| `dist\officepack-便携单文件（启动慢）.exe` | 25~45 秒 | 命令行版单文件；**不含本轮新增的 `--no-split` / `unpack -`**，需要这两个请用目录版 |

目录版是绿色软件：把整个文件夹拷走就能用，删掉即卸载。
单文件版每次启动都要把 17MB 运行时解压到临时目录，**实测 20~45 秒**（被杀软反复扫描时更慢），
只适合「必须只发一个文件」的场合。日常使用请用目录版。

## 迁移到另一台电脑

目录版是 **1122 个文件**（其中 `_internal` 里 1121 个，几乎全是 Tcl/Tk 脚本和 Python 运行时）。
逐个文件拷贝极易丢文件，**必须整包传输**：

| 传什么 | 大小 | 用法 |
|---|---|---|
| `dist\OfficePack-GUI-win64.zip` | 16.7 MB | **首选**。传过去解压，得到 `OfficePack-GUI` 文件夹，双击里面的 `启动.bat` |
| `dist\修复包-_tk_data.zip` | 269 KB | **应急**。只补 `_internal\_tk_data` 一个目录，解压到 `OfficePack-GUI` 目录下覆盖 |

### 报错 `Tk data directory "..._internal\_tk_data" not found`

这是**丢文件**，不是程序 bug（`_internal\_tk_data` 里有 89 个 Tcl/Tk 文件，缺了整个界面库就起不来）。

修复顺序：

1. **应急**：解压 `修复包-_tk_data.zip` 到 `OfficePack-GUI` 目录（覆盖），再双击 `启动.bat`
2. **彻底**：删掉旧文件夹，重新解压 `OfficePack-GUI-win64.zip`
3. 之后**都从 `启动.bat` 进**，它会先检查 6 个关键文件，缺了直接告诉你缺哪个

### 判断是不是安全软件在删

打开 `_internal` 看两个目录：

- `_tcl_data` 在、`_tk_data` 不在 → **传输丢了一个子目录**，重新整包传即可
- 两个都不在（或 `.tcl` 文件被清零）→ **安全软件按扩展名在删**，需联系 IT 加白名单；这种情况下压缩包解压后也会被删，建议改用单文件版

**图形界面用法**：拖入文件 → 选预设和口令 → 点「开始处理」。

- 处理中按钮显示「处理中…」，进度条实时推进
- **完成后弹窗汇总成功/失败数量，并显示输出文件夹的完整路径**，可直接点「是」打开该文件夹
- 有失败时弹窗给出每个文件的失败原因（如口令错误、文件被占用）
- 右侧常驻「打开输出文件夹」按钮，事后也能一键定位产物
- 输出目录留空时，产物保存在**源文件所在目录**
- **「分片输出」默认不勾**，需要切段时才勾上并填每段字符数
- **「粘贴文本还原…」**：不存文件也能还原，多个分片可粘进同一个文本框
- **每个参数名后面的蓝色 `?`** 点开就是该项说明（每个选项的差别、当前选中项高亮）；底部「全部参数说明…」可一次看完

命令行（在 `dist\officepack\` 里）：

```bash
# 打包（字符数最少 + AES-256-GCM 加密）
officepack.exe pack 报表.docx --preset chars --password 123456

# 校验（只验证能否完整还原，不写文件）
officepack.exe verify 报表.docx.cjk.opk.txt --password 123456

# 查看元信息
officepack.exe inspect 报表.docx.cjk.opk.txt

# 还原
officepack.exe unpack 报表.docx.cjk.opk.txt -o 输出目录 --password 123456
```

源码方式运行（开发调试用）：`python -m officepack <子命令>`，或双击 `officepack.cmd`。

```bash
build_exe.cmd            # 构建目录版（推荐）：构建 → 自动瘦身
build_exe.cmd portable   # 额外构建单文件便携版
```

三步流水线，缺一不可：

| 步骤 | 脚本 | 干什么 |
|---|---|---|
| 1 | `scripts/reset_dist.py` | 把旧产物挪进 `dist_prev/`（重名自动加序号）。**必须在构建前**，否则 PyInstaller 的 COLLECT 要删 1300 个文件，会被安全策略/杀软拦住，表现为「打印 Build complete 但产物是旧的」 |
| 2 | `pyinstaller` | 分别构建 GUI / CLI 的目录版 |
| 3 | `scripts/trim_dist.py` | 删掉确定用不到的运行时文件（见下） |

> 程序运行时 `dist` 里的 exe 和 dll 被系统独占，覆盖会失败。

自检依赖是否完整（弹窗显示 tkinter / 拖拽库 / cryptography 状态）：
`OfficePack-GUI.exe --selftest`

### 瘦身：为了 60MB → 41MB

`--collect-all PIL` 会把整个 Pillow 拖进来，其中大头是**完全用不到的编解码器**：

| 删掉的 | 省 | 为什么可以删 |
|---|---|---|
| `PIL/_avif.pyd` | 7.5 MB | AVIF 编解码。二维码只出 PNG，扫码只碰 png/jpg/bmp/gif/webp |
| `PIL/_imagingft.pyd` | 2.1 MB | FreeType 字体渲染。二维码是方块拼的，不写文字 |
| `tkinterdnd2/tkdnd/` 11 个平台 | 1.3 MB | 只留 `win-x64`，osx/linux/arm 的拖拽库对本包无用 |
| `PIL/_imagingcms.pyd` | 264 KB | LittleCMS 色彩管理，不做色彩空间转换 |
| `_zstd.pyd` / `_decimal.pyd` | 776 KB | zstd 解压、十进制加速，本项目都不碰 |

`_tcl_data/tzdata`（1.1MB）**故意保留**：它一个目录里 643 个文件，一次删光会撞上
沙箱的批量删除保护，收益不值这个风险。

> 瘦身是「锦上添花」，任何一项删失败都只警告、不让构建失败；
> 删完必须跑 `scripts/verify_release.py` 证明功能没坏（它检查的就是被删文件没被依赖）。

## 配置怎么选（速查）

图形界面里每个参数名后面都有个蓝色 **?**，点一下就能看到「这个参数是干什么的、每个选项差别在哪」，
当前选中的选项会带 ▶ 标记；右侧底部「全部参数说明…」可以一次看完。

| 你的实际限制 | 怎么配 | 为什么 |
|---|---|---|
| 每次只能输入 N 个**字** | 预设 `chars`，需要时勾「分片输出」填 N | cjk 一个汉字装 14 bit，字符数最少 |
| 按**字节**限额（邮件、短信、接口） | 预设 `compact` | base91 是纯 ASCII 里最紧凑的，字符数少且每字符 1 字节 |
| 粘贴后可能被改大小写 / 插转义符 | 预设 `safe` | 纯大写字母+数字，没有任何符号可被破坏 |
| 文件很小、要人工核对 | 预设 `plain` | 不压缩，肉眼能看出是 base64 |
| 不想让别人看到内容 | 加密器 `aes-256-gcm` + 填口令 | 同时防篡改，改 1 个字符就解不开 |
| 内容是 jpg / png / zip 这类已压缩文件 | 压缩器 `auto` 或 `none` | 再压没有收益，`auto` 会自动跳过，不会越压越大 |
| 文档里全是重复的中文条款 | 压缩器 `max` | 多组 lzma 参数逐个试，压得最狠（但最慢） |

## 预设

| 预设 | 编码器 | 压缩 | 说明 |
|---|---|---|---|
| `chars` | cjk | max | **字符数最少**，冲万字级目标用这个 |
| `compact` | base91 | auto | ASCII 体积最小 |
| `safe` | base32 | auto | 纯大写字母+数字，邮件/IM/Excel 粘贴不会被转义 |
| `fast` | base64 | zlib | 速度优先 |
| `plain` | base64 | none | 不压缩，最透明 |
| `自定义` | 手动 | 手动 | 改下面任意一项，预设会自动变成「自定义」 |

## 编码器与压缩器

编码器（膨胀率 = 文本字符数 / 原始字节数）：

| 编码器 | 字符/字节 | 特点 |
|---|---|---|
| `cjk` | **0.571×** | 汉字编码（每 14 bit 一个汉字），**字符数最少**，比 base91 再少 54% |
| `base91` | 1.231× | ASCII 下最紧凑，字母表已排除 `-` `'` `\` |
| `base85` | 1.250× | 紧凑，但含 `"` `'` `\`，部分渠道会转义 |
| `base64` | 1.334× | 最通用 |
| `base32` | 1.600× | 纯大写+数字，最耐复制粘贴 |
| `hex` | 2.000× | 最直观可审计 |
| `custom` | 1.334× | 自定义 64 字符码表（`--alphabet`），带码表置换 |

压缩器：`max`（多组 lzma 参数逐个试，取最小）/ `auto`（试 lzma，无收益自动跳过）/ `lzma` / `zlib` / `bz2` / `none`。

## 万字级目标与分段

> 下面的示例用 `python -m officepack` 表示命令；如果你用的是 exe，换成 `dist\officepack\officepack.exe`。

```bash
# 默认整份输出，不分片
python -m officepack pack 报告.docx --preset chars

# 目标：整份文档的文本总量压到 1 万字以内
python -m officepack pack 报告.docx --preset chars --target 10000

# 需要切段时才显式开启：每段最多 1 万字
python -m officepack pack 报告.docx --preset chars --split 10000 --password 123456

# 强制整份输出，覆盖已有的分段设置
python -m officepack pack 报告.docx --preset chars --split 10000 --no-split
```

**是否分片是显式开关**：

| 场景 | 做法 |
|---|---|
| 不分片（默认） | 什么都不加；或加 `--no-split` 强制覆盖 |
| 按字符数切 | `--split N` |
| 切成固定段数 | `--parts K` |

图形界面里对应右侧的「分片输出」复选框：**默认不勾**，勾选后才能填「字/段」，切到还原模式时自动置灰。

**1 万字能装多少，取决于文档的信息量**（1 个汉字承载 14 bit，1 万字 ≈ 17.5KB 不可压缩数据）：

| 文档类型 | 原始大小 | 结果 |
|---|---|---|
| 纯中文正文 4,000 条 | 311 KB | ✓ 1,120 字 |
| 高度重复文本 | 630 KB | ✓ 131 字 |
| 随机二进制 | 8 KB | ✓ 4,572 字 |
| 随机二进制 | 17.5 KB | ✓ 10,000 字（正好上限） |
| 随机二进制 | 50 KB | ✗ 需 28,572 字 = 2.9 段 |
| 含 500KB 图片的 docx | 500 KB | ✗ 需 28.6 段 |

**结论**：纯文字类文档几乎都能进 1 万字；含图片/嵌入对象的文档，图片本身已是压缩格式，无损还原下无法再压，只能分段。

分段格式（每段可独立发送，乱序收集也能拼回）：

```
#OPK1 cae6c6 003/012 l).)@ 9282
<该段载荷，每行 100 字符>
```

头部字段：文档 ID / 序号 / 总段数 / 段 CRC32 / 段字符数。
最后一位让解析器精确截断——**段尾多粘了无关文字会被自动忽略**，不会破坏校验。

还原时把全部段一起传入即可（顺序随意）：

```bash
# 从文件还原，分片可一次给多个
python -m officepack unpack part*.txt --password 123456

# 不用存文件：把分片文本从管道喂进去
type part*.txt | officepack.exe unpack - --password 123456
```

**手动输入文本还原**：图形界面右侧有 **「粘贴文本还原…」** 按钮，把容器文本直接粘进文本框即可，
不用先存成文件。支持三种形态：

- 一整个完整容器
- 单个分片
- **多个分片全粘在同一个文本框里**，顺序随意，段与段之间夹说明文字也不影响

对话框里有「检查分片」，会实时显示 `共 24 段，已收 5 段，缺第 6、7、8…段`，
凑齐了再点「还原」，避免白试一次。

缺段、重复段、单段被改动，都会明确报错并指出是第几段。

实测（含 1.5MB 图片的 docx，1,500,594 字节）：

| 方案 | 文本体积 |
|---|---|
| base32 + zlib | 2,426,278 B |
| base64 + zlib | 2,022,016 B |
| base85 + lzma | 1,895,329 B |
| **base91 + auto** | **1,864,514 B**（比 base32 省 23%） |

未压缩的文本型 doc（1,260,000 字节）：`base32+zlib` → 5,659 B，`base91+auto` → **1,066 B**（省 81%）。

## 运行环境（Python 版本）

**用 exe 的话，机器上不需要 Python。** 打成 exe 时已经把 Python 3.14 运行时 +
全部依赖（Pillow / cryptography / qrcode / zxing-cpp）一起封进去了，
目标机器只要 Windows 10/11 64 位、双击就能跑。

从源码跑才需要 Python，要求与依赖一致：

| 组件 | 要求 |
|---|---|
| Python | **3.8 或更高**（Pillow ≥ 10 起的门槛；3.7 装不了 Pillow 10） |
| Pillow | ≥ 10.0（二维码出图、GIF、截图） |
| cryptography | ≥ 41.0（只加密时需要） |
| qrcode | ≥ 8.0（二维码出图） |
| zxing-cpp | ≥ 2.2（二维码识别） |
| tkinterdnd2 | 可选，装了才能拖拽文件 |

代码本身没有用 3.9+ 的语法或运行库特性，所以 3.8 能跑；但**更高版本更省心**——
项目全程在 **Python 3.14** 上开发和验证（91 项测试 + exe 就是用 3.14 打的）。
3.13 / 3.14 不存在「太新跑不了」的问题。

> 常见误解：`from __future__ import annotations` 让所有类型注解都变成字符串，
> 所以 `list[str]` / `str | None` 这种写法在 3.8 上也不会报错。

## 二维码通道

文本之外，也可以把文件做成**二维码图片**：走扫码工具（AirScan-QR、鹊桥之类）跨网传输，
或者干脆截图再扫回来。还原依旧是逐字节一致。

```bash
# 打包成二维码：一张放不下会自动拆成多帧
python -m officepack pack 报告.docx --qr

# 想尽量一张搞定 —— 用二维码专用预设（qr45 + lzma max）
python -m officepack pack 报告.docx --qr --preset qr

# 额外输出循环播放的 GIF 动图（手机对着屏幕扫）
python -m officepack pack 报告.docx --qr --preset qr --qr-gif 3

# 指定输出目录、纠错级别、每帧字符数
python -m officepack pack 报告.docx --qr -o out --qr-ec M --qr-chars 1500

# 只写总览图，不写 N 张单帧 PNG（总览里每张码和单帧同尺寸，识别总览就够了）
python -m officepack pack 报告.docx --qr --no-single

# 反过来：只要单帧、不要总览图
python -m officepack pack 报告.docx --qr --no-sheet

# 从图片还原：给 PNG、给目录、给 GIF、给多张截图都行
python -m officepack unpack out
python -m officepack unpack 截图1.png 截图2.png
python -m officepack unpack 动图.gif
```

图形界面里：右侧「输出二维码 → 生成」勾选框 + 格式下拉
（`PNG（单帧 + 总览）` / `PNG（仅总览）` / `GIF 动图` / `PNG + GIF`）+ 帧率。

还原走「**还原二维码 ▾**」下拉，四条路：

| 入口 | 适合 |
|---|---|
| **粘贴识别面板…** | 一张张截图累加（Ctrl+V 贴图），能连 Ditto，缺帧会告诉你缺第几帧 |
| **框选屏幕区域…** | 屏幕上就有码，拖个框就开始**连拍**：动图边播边收，收齐自动停；**多屏全覆盖**，跨屏也能框 |
| **读取剪贴板截图** | 刚截的图还在剪贴板里，一次搞定 |
| **选择图片文件…** | 多选也全部识别后合并，不是只认最后一张 |

### 一张码能装多少（物理上限）

二维码 v40 在**字母数字模式**下的容量（字符）：

| 纠错级别 | 容量 | 说明 |
|---|---|---|
| **L** | 4,296 | 默认。容量最大，屏幕截图场景够用 |
| M | 3,391 | 有轻微污损/缩放时更稳 |
| Q | 2,420 | 打印后拍照、折痕场景 |
| H | 1,852 | 最耐污损，容量最小 |

上限就是这样：4,296 字符 × 5.5 bit ÷ 8 = **2,953 字节**，任何编码都突破不了。

`--preset qr` 用的是 `qr45` 编码器（2 字节 → 3 字符，字符集是二维码的 44 个字母数字符号），
比 `base32`（1.6 字符/字节）少占 6.7%，是这份容量里能榨出的最后一点。实测单张上限：

| 场景 | 单张码最大装多少（压缩后） |
|---|---|
| 不加密 + `qr45` + L | **2,495 字节** |
| AES-256-GCM 加密 + `qr45` + L | **2,357 字节** |
| 同上但用 `base32` | 2,077 字节（v1.2 之前的口径） |

编码器对帧数的影响很大，**用默认的 `cjk` 出码会多出 4.7 倍帧数**：

| 编码器 | 每字符占 bit | 相对 `qr45` 的帧数 | 什么情况下值得用 |
|---|---|---|---|
| `qr45` | 5.5（字母数字模式） | 1.0× | **二维码一律选这个** |
| `base32` / `hex` | 5.5（字母数字模式） | 1.07× / 1.33× | 要人能念出来时用 base32 |
| `base91` / `base64` / `base85` | 8.0（字节模式） | ≈1.4× | 想让文本本身更短、且不走二维码 |
| `cjk` | 24.0（UTF-8 汉字） | ≈4.7× | 追求字符数时用，二维码里最费 |

按 2.4 KB 单张上限估算：

| 文件 | 压缩后 | 帧数 |
|---|---|---|
| 3 KB 源码 / Markdown | ~1.4 KB | **1 张** |
| 8 KB 源码 | ~3 KB | 2 张 |
| 21 KB Markdown（本 README） | 9.2 KB | 4 张 |
| 103 KB 的 `python.exe` | 50 KB | 19 张（3 页总览图） |
| 2 KB 的 docx | 1.4 KB | **1 张** |

> 一句话：**压缩后 2.4 KB 以内才能一张搞定**。文本/源码类大约对应 8~12 KB 的原文件；
> docx/zip/pdf 本身已压缩，差不多 1:1，所以只有 2 KB 出头的小文档能单码。

### 静态还是动态

两种都能出，界面上可选：

| 格式 | 适合 | 怎么读 |
|---|---|---|
| **PNG 单帧 + 总览图** | 电脑上还原 | 总览图一张图里有多张码，`unpack` 一次全部识别；也可框选屏幕 |
| **PNG 仅总览** | 不想收一堆 PNG | 只留总览图。总览里的每张码是**原尺寸拼贴、没有任何缩放**，一帧的信息和单帧图完全相同，识别总览就等于识别单帧 |
| **GIF 动图** | 手机扫 / 电脑框选 | 循环播放，相机逐帧抓；**首尾带标识帧**（见下节），框选时能判断一轮起止；也能把 `.gif` 当文件直接丢给 `unpack` |
| **PNG + GIF** | 不确定用哪端 | 两套都出 |

GIF 对二维码是**无损**的：只有黑白两色，2 色调色板 + LZW 不做任何量化。
所有帧统一成**同一像素尺寸**（按最大的那帧算模块大小、其余居中补白）—— 尺寸不一致时
GIF 逻辑画布按首帧走，比画布大的帧会被裁掉右/下边，播放器里就是个残缺码，
怎么扫都扫不出来（1.4.1 修的真 bug）。
但体积不会比 PNG 更小 —— 各帧图案完全不同，GIF 的帧间压缩用不上：

| 输出（4 帧，960px） | 体积 |
|---|---|
| 4 张单帧 PNG | 69 KB |
| 1 张总览图 PNG | 72 KB |
| 1 张 GIF | 131 KB |

想压体积就**降分辨率**：二维码识别看的是「每模块几个像素」，3 px 就够（v40 是 185 模块，
555 px 即可），不必 5 px。`--qr-px 600` 能省 30%~40%，识别率不受影响。

### 框选怎么收动图（首帧开始、尾帧结束）

屏幕上播着动图时，**一张截图只能拿到其中一帧**，靠单次截图必然缺帧。所以框选拖完
松手后不是截一张，而是**对着这块区域连拍**：

- **首尾标识帧**：GIF 首帧是 `#OPKmark|S|<文档ID>|<总帧数>`，尾帧是 `#OPKmark|E|<文档ID>`。
  识别端**见 S 才认为一轮开始、见 E 才认为一轮结束**，不用猜播放相位
- 一轮没收齐？画面继续播，自动接着收下一轮；连续两轮颗粒无收才收工
- 静态码第一枪就齐，立刻返回，不会干等
- 漏掉的帧**再框一次会自动续上**（已收的攒着，不重复、不用从头来）
- 画面没变化的帧直接跳过解码（指纹去重），所以采样能追上 3 帧/秒的播放速度
- 旧动图（没有标识帧）照样能用：退化成「连续 3 秒没有新帧就收工」

实测（7 帧数据 + 首尾标识、3 帧/秒播放、真实屏幕框选）：**2.4 秒收全 7/7，还原逐字节一致**。

### 多帧怎么收（顺序无关）

每张图都是一个自包含的 `#OPK1` 分段，段头写明 `文档ID / 序号 / 总段数 / CRC`：

- **顺序完全无关**：按段头序号重组，倒着扫、跳着扫都行
- **多张图一起给**：截图、单帧图、总览图混在一起也全部识别后合并（不是只认最后一张）
- 扫重了无害：内容相同的重复帧自动忽略
- 扫花了无害：CRC 不过的帧被丢弃，好帧照样拼得回去
- 少一帧会明确告诉你「缺少第 3 段」；如果同时有坏帧，会提示「重扫这几张」
- 同一序号出现两份**不同**内容（两次打包混在一起）→ 直接报错，绝不瞎猜
- 总览图每页 12 帧，多页自动续（19 帧 = 2 页），截两次图就能全覆盖
- 最终还有整文件 SHA-256 收口，任何一位不对都会报出来

### 屏幕水印 / 软件水印

真正麻烦的不是图片文件自带的痕迹，而是**图片显示在屏幕上时**被叠上去的水印：
公司的屏幕监控水印、看图软件/Office 预览加的半透明角标、远程桌面叠加的会话标记。
框选截图会把这层水印一起截进来，直接识别就会掉帧。

识别时不会只试一次原图，而是自动做一轮**像素级净化**再识别，从便宜的往下试，
捞到新帧就继续、收全就停（单张图总预算 6 秒，绝不卡界面）：

| 顺序 | 处理 | 针对什么 |
|---|---|---|
| 1 | 固定阈值二值化（60/80/100/120 四档） | 半透明浅灰水印：码是纯黑，低阈值把「不够黑」的像素全漂白 |
| 2 | Otsu 自适应阈值 | 整体偏暗/偏亮的截图、压缩噪点 |
| 3 | 反色 | 深底浅码（某些看图软件的反色模式） |
| 4 | R/G/B 单通道 | 彩色水印（蓝底白字），单通道里对比度最高 |
| 5 | 2 倍 / 3 倍放大 | 码在屏幕上被缩得很小，每模块不足 2 px |
| 6 | 中值滤波 | 细线状水印 |
| 7 | 重叠切块（2×2 + 12% 重叠） | 大图局部遮挡、水印整块压在某个角上 |

实测（6 帧总览图，铺满整幅的半透明水印 + JPEG 压缩 + 缩放，括号内为只跑原图的结果）：

| 场景 | 只跑原图 | 自动净化 |
|---|---|---|
| 缩放 70% + 水印 + JPEG85 | 6/6 | 6/6 |
| 缩放 55% + 重水印 + 角标 + JPEG80 | 6/6 | 6/6 |
| 缩放 60% + 蓝色水印 + JPEG75 | 6/6 | 6/6 |
| 缩放 35%（每帧约 290 px） | 5/6 | **6/6** |
| 缩放 30%（每帧约 246 px） | 1/6 | **6/6** |
| 缩放 28%（每帧约 230 px） | 1/6 | **5/6** |
| 0.8 不透明度灰字铺满 | 3/6 | **6/6** |

最后一档 28% 还差一帧、24% 基本认不出来 —— 那是**分辨率物理极限**（v40 是 177 模块，
每模块只剩 1 px），任何算法都无解。这时候把图放大到 100% 再截一张，或者用粘贴面板
逐张补，比死磕算法靠谱。

### 多屏与剪贴板

- **框选铺满所有屏幕**：遮罩按 Windows 的「虚拟桌面」尺寸铺，主屏、副屏、副屏在主屏
  左侧导致的负坐标都覆盖；拖动能跨屏，抓图按虚拟桌面坐标取。以前只铺鼠标所在那一块，
  另一块屏不暗也点不到，双屏用户会以为功能坏了。
- **剪贴板直读**：不再依赖 Pillow 的 `grabclipboard()` 只认最前面一项；直接读
  `PNG / CF_DIBV5 / CF_DIB / CF_BITMAP / CF_HDROP`，Ditto 放进去的 `CF_DIB` 也能读出来。
- **Ditto 兼容**：自动探测 `Ditto.exe`（运行中的进程 → 卸载注册表 → PATH → 环境变量与
  各本地盘符的常见目录，**不写死任何路径**）。点「打开 Ditto 剪贴板」把历史窗口叫出来，
  在里面双击要用的图，Ditto 会把它贴进面板，自动识别累积。
- 没装 Ditto 就走兜底：`Win+Shift+S` 截一张 → 回面板 `Ctrl+V`，效果一样。

### 识别不到怎么办

1. 让整张码**完整入镜**，四周留白（静区）别裁掉
2. 不要缩小、不要加滤镜/锐化；屏幕截图直接存 PNG 最稳
3. 手机拍屏幕会有摩尔纹，改用截图
4. **码太小**是最常见原因：把图放大到 100% 或全屏再截图；用总览图时尽量让每帧 ≥ 400 px
5. 缺帧时用「粘贴识别面板」逐张补 —— 顺序完全无所谓，缺第几帧会明确告诉你
6. 图太小扫不出来时，降低纠错级别（L）或调小 `--qr-chars` 让每张码更宽松
7. **动图框选**：让它在框里一直循环播放，别停在某一帧；一轮没收齐会自动再等一轮，
   还缺的话再框一次同一块区域即可（已收的会累加，不必从头来）

## 文本容器格式

```
-----BEGIN OFFICEPACK v1-----
Meta: eyJ2IjoxLCJuYW1lIjoi...          ← base64(JSON)：文件名/大小/SHA-256/算法参数
Info: 报表.docx | 48213 B | text=59187 chars | codec=base91 | compress=lzma | cipher=aes-256-gcm
Preview:                                ← 人可读正文预览（不参与还原，可用 --no-preview 关闭）
  | 第一章 总述
Payload:                                ← 纯 ASCII 载荷，每行 100 字符
MZXW6YTBOI...
-----END OFFICEPACK v1-----
```

还原只依赖 `Meta` + `Payload`，`Info` / `Preview` / 注释行全部忽略，
所以文本可以随意加前后缀、被邮件折行、被 IM 截断后拼接回来。

`--ascii-only` 可让整个文件严格 7-bit ASCII（注释区中文转 `\uXXXX`）。

## 安全

- **AES-256-GCM**，密钥由口令经 **scrypt**(n=16384, r=8, p=1) 派生
- 每块独立 nonce（8B 随机前缀 + 4B 计数器），分块 1 MiB，内存占用与文件大小无关
- AAD 绑定原始大小与 SHA-256 → 元信息被改动会导致解密直接失败
- 任意一位翻转都会触发 GCM 认证失败或 SHA-256 校验失败

## 限制

- 老格式 `doc / xls / ppt` 不生成文字预览（无法解析 OLE2），但**无损还原完全支持**
- `cjk` 编码器字符数最少，但 UTF-8 字节数约为原始的 1.71 倍——只适合「按字符数限制」的渠道；
  若渠道限制的是字节数，请用 `base91`
- 打包需全量读入内存，峰值约为文件大小的 3~4 倍；几十 MB 的文档无压力
- 依赖 `cryptography`（仅加密时需要），未安装时可用 `--cipher none`
- **单张二维码最多装 2.4 KB（压缩后）**，这是 QR 标准的物理上限，换编码器也只能多 6.7%。
  所以二维码天然只适合几 KB ~ 几十 KB 的文件；更大文件会拆成很多帧，建议走文本通道
- 二维码通道**不限定编码器**，但 `base91/base64/cjk` 会掉出「字母数字模式」，
  同样内容多占 1.4~4.7 倍帧数；**出码一律用 `--preset qr`**
- GIF 动图无法被 `PIL` 当作静态图一次读全 —— 但本工具的 `unpack` 会逐帧识别，直接给它 `.gif` 即可

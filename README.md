# officepack — 任意文件 ⇄ 纯文本 无损装换

把**任意文件**（`doc/docx/xls/xlsx/ppt/pptx`、`pdf`、`zip/rar/7z`、`md/java/sql/py` 源码、
图片、音视频……）打包成一段**纯文本**，之后用这段文本 **100% 还原**出原文件 ——
还原后 SHA-256 与原文件逐字节一致。

```
报表.docx ──打包──> 报表.docx.base91.opk.txt  （纯 ASCII 文本，可加密）
报表.docx.base91.opk.txt ──还原──> 报表.docx   （SHA-256 完全一致）
```

> **不想自己构建？** 直接下打包好的 exe：
> [**Releases（最新版）**](https://github.com/qq928820655/officepack/releases/latest)
> —— 图形界面版（推荐）、单文件便携版、命令行版、应急修复包。

## 支持哪些文件

**结论：任意文件都能装。** 底层走的是「原始字节 → 压缩 → 加密 → 编码」，
不解析文件内容，所以只要求「能读出来」，不要求「认得这个格式」。

| 类别 | 扩展名 | 预览 |
|---|---|---|
| Office（OOXML） | `docx/docm/xlsx/xlsm/pptx/pptm` | 抽正文 |
| Office（老二进制） | `doc/xls/ppt/msg` | 扫可打印串 |
| PDF | `pdf` | 解 FlateDecode 流抽字符串 |
| 压缩包 | `zip/jar/apk/war/whl/odt/epub…` | 列目录 + 条目数 |
| 压缩包（无标准库） | `rar/7z/tar/gz/xz` | 仅类型标注 |
| 源码 / 文本 | `md/java/sql/py/js/ts/go/rs/json/xml/yaml/ini/log…` | 按 UTF-8 → GBK 解码 |
| 图片 | `png/jpg/bmp/gif/webp/tif` | 格式 + 像素尺寸 |
| 音视频 / 可执行 / 未知 | `mp3/mp4/exe/dll/…`、任意扩展名 | 无（不影响还原） |

预览只是**给人看的注释**，抽不出来（例如 `rar`、`mp4`）也完全不影响无损还原。

## 为什么不是「提取文字再还原」

Word 二进制（OLE2）和 docx（ZIP+XML）里包含样式表、压缩流、字体嵌入、修订记录、图片。
**把正文抽成纯文本后，这些信息永久丢失，无法还原成原文件。**

所以本工具采用「编码载体」路线：

```
原始字节 → 压缩 → 加密 → 编码成可打印 ASCII → 文本
文本 → 解码 → 解密 → 解压 → 原始字节（SHA-256 校验）
```

正文预览只是**附赠给人看的注释**，不参与还原。

## 快速开始

**免安装，双击即用**（目标机器不需要装 Python，Windows 10/11 64 位）：

| 产物 | 启动速度 | 说明 |
|---|---|---|
| `dist\OfficePack-GUI\OfficePack-GUI.exe` | **1~3 秒** | 图形界面，支持拖拽，**推荐**（从同目录 `启动.bat` 进，会先自检） |
| `dist\OfficePack-GUI-win64.zip` | — | 整个 GUI 目录的压缩包，**换电脑时传这个** |
| `dist\officepack\officepack.exe` | **0.5 秒** | 命令行版 |
| `dist\OfficePack-GUI-便携单文件（启动慢）.exe` | 45 秒 | 只有这一个文件，拷走即用；功能与目录版一致 |
| `dist\officepack-便携单文件（启动慢）.exe` | 25~45 秒 | 命令行版单文件；**不含本轮新增的 `--no-split` / `unpack -`**，需要这两个请用目录版 |

目录版是绿色软件：把整个文件夹拷走就能用，删掉即卸载。
单文件版每次启动都要把 17MB 运行时解压到临时目录，**实测 20~45 秒**（被杀软反复扫描时更慢），
只适合「必须只发一个文件」的场合。日常使用请用目录版。

## 迁移到另一台电脑

目录版是 **1122 个文件**（其中 `_internal` 里 1121 个，几乎全是 Tcl/Tk 脚本和 Python 运行时）。
逐个文件拷贝极易丢文件，**必须整包传输**：

| 传什么 | 大小 | 用法 |
|---|---|---|
| `dist\OfficePack-GUI-win64.zip` | 16.7 MB | **首选**。传过去解压，得到 `OfficePack-GUI` 文件夹，双击里面的 `启动.bat` |
| `dist\修复包-_tk_data.zip` | 269 KB | **应急**。只补 `_internal\_tk_data` 一个目录，解压到 `OfficePack-GUI` 目录下覆盖 |

### 报错 `Tk data directory "..._internal\_tk_data" not found`

这是**丢文件**，不是程序 bug（`_internal\_tk_data` 里有 89 个 Tcl/Tk 文件，缺了整个界面库就起不来）。

修复顺序：

1. **应急**：解压 `修复包-_tk_data.zip` 到 `OfficePack-GUI` 目录（覆盖），再双击 `启动.bat`
2. **彻底**：删掉旧文件夹，重新解压 `OfficePack-GUI-win64.zip`
3. 之后**都从 `启动.bat` 进**，它会先检查 6 个关键文件，缺了直接告诉你缺哪个

### 判断是不是安全软件在删

打开 `_internal` 看两个目录：

- `_tcl_data` 在、`_tk_data` 不在 → **传输丢了一个子目录**，重新整包传即可
- 两个都不在（或 `.tcl` 文件被清零）→ **安全软件按扩展名在删**，需联系 IT 加白名单；这种情况下压缩包解压后也会被删，建议改用单文件版

**图形界面用法**：拖入文件 → 选预设和口令 → 点「开始处理」。

- 处理中按钮显示「处理中…」，进度条实时推进
- **只有一条 6px 的进度条**，显示**当前文件内部**走到哪了
  （`渲染 PNG 45% (58/129) · 3.2s`）；多文件时文字前面带 `2/5 ·`
  - 以前是两条（文件级 + 帧级），文件级在处理单个文件时永远停在 0/100%，白占 22px
  - 只在**有活干**的时候出现；空闲时自动收起，日志下面不会留空杠
  - 右侧文字先排版、再排进度条，不会被挤出窗口只剩半截
- **日志框默认 14 行**，屏幕不够时自动往下压（压到 2 行为止）；
  操作模式、预设/分片并排成一行，省下的高度全给日志
- **日志每 10% 留一行**，长任务一秒一跳心跳，事后翻日志能看出哪一步花了多久
- **完成后弹窗汇总成功/失败数量，并显示输出文件夹的完整路径**，可直接点「是」打开该文件夹
- 有失败时弹窗给出每个文件的失败原因（如口令错误、文件被占用）
- 右侧常驻「打开输出文件夹」按钮，事后也能一键定位产物
- 输出目录留空时，产物保存在**源文件所在目录**
- **「分片输出」默认不勾**，需要切段时才勾上并填每段字符数
- **「粘贴文本还原…」**：不存文件也能还原，多个分片可粘进同一个文本框
- **每个参数名后面的蓝色 `?`** 点开就是该项说明（每个选项的差别、当前选中项高亮）；
  「选项」标题右侧的 `?` 可一次看完

命令行（在 `dist\officepack\` 里）：

```bash
# 打包（字符数最少 + AES-256-GCM 加密）
officepack.exe pack 报表.docx --preset chars --password 123456

# 校验（只验证能否完整还原，不写文件）
officepack.exe verify 报表.docx.cjk.opk.txt --password 123456

# 查看元信息
officepack.exe inspect 报表.docx.cjk.opk.txt

# 还原
officepack.exe unpack 报表.docx.cjk.opk.txt -o 输出目录 --password 123456
```

源码方式运行（开发调试用）：`python -m officepack <子命令>`，或双击 `officepack.cmd`。

## 重新构建 exe

```bash
build_exe.cmd            # 构建目录版（推荐）：构建 → 自动瘦身
build_exe.cmd portable   # 额外构建单文件便携版
```

三步流水线，缺一不可：

| 步骤 | 脚本 | 干什么 |
|---|---|---|
| 1 | `scripts/reset_dist.py` | 把旧产物挪进 `dist_prev/`（重名自动加序号）。**必须在构建前**，否则 PyInstaller 的 COLLECT 要删 1300 个文件，会被安全策略/杀软拦住，表现为「打印 Build complete 但产物是旧的」 |
| 2 | `pyinstaller` | 分别构建 GUI / CLI 的目录版 |
| 3 | `scripts/trim_dist.py` | 删掉确定用不到的运行时文件（见下） |

> 构建前脚本会自动结束正在运行的 `OfficePack-GUI.exe` / `officepack.exe`——
> 程序运行时 `dist` 里的 exe 和 dll 被系统独占，覆盖会失败。

自检依赖是否完整（弹窗显示 tkinter / 拖拽库 / cryptography 状态）：
`OfficePack-GUI.exe --selftest`

> 构建脚本固定使用 `C:\Python314\python.exe`——托管 Python 3.13 缺 tkinter 和 cryptography。

### 瘦身：为了 60MB → 41MB

`--collect-all PIL` 会把整个 Pillow 拖进来，其中大头是**完全用不到的编解码器**：

| 删掉的 | 省 | 为什么可以删 |
|---|---|---|
| `PIL/_avif.pyd` | 7.5 MB | AVIF 编解码。二维码只出 PNG，扫码只碰 png/jpg/bmp/gif/webp |
| `PIL/_imagingft.pyd` | 2.1 MB | FreeType 字体渲染。二维码是方块拼的，不写文字 |
| `tkinterdnd2/tkdnd/` 11 个平台 | 1.3 MB | 只留 `win-x64`，osx/linux/arm 的拖拽库对本包无用 |
| `PIL/_imagingcms.pyd` | 264 KB | LittleCMS 色彩管理，不做色彩空间转换 |
| `_zstd.pyd` / `_decimal.pyd` | 776 KB | zstd 解压、十进制加速，本项目都不碰 |

`_tcl_data/tzdata`（1.1MB）**故意保留**：它一个目录里 643 个文件，一次删光会撞上
沙箱的批量删除保护，收益不值这个风险。

> 瘦身是「锦上添花」，任何一项删失败都只警告、不让构建失败；
> 删完必须跑 `scripts/verify_release.py` 证明功能没坏（它检查的就是被删文件没被依赖）。

## 配置怎么选（速查）

图形界面里每个参数名后面都有个蓝色 **?**，点一下就能看到「这个参数是干什么的、每个选项差别在哪」，
当前选中的选项会带 ▶ 标记；「选项」标题右侧的 `?` 可以一次看完。

| 你的实际限制 | 怎么配 | 为什么 |
|---|---|---|
| 每次只能输入 N 个**字** | 预设 `chars`，需要时勾「分片输出」填 N | cjk 一个汉字装 14 bit，字符数最少 |
| 按**字节**限额（邮件、短信、接口） | 预设 `compact` | base91 是纯 ASCII 里最紧凑的，字符数少且每字符 1 字节 |
| 粘贴后可能被改大小写 / 插转义符 | 预设 `safe` | 纯大写字母+数字，没有任何符号可被破坏 |
| 文件很小、要人工核对 | 预设 `plain` | 不压缩，肉眼能看出是 base64 |
| 不想让别人看到内容 | 加密器 `aes-256-gcm` + 填口令 | 同时防篡改，改 1 个字符就解不开 |
| 内容是 jpg / png / zip 这类已压缩文件 | 压缩器 `auto` 或 `none` | 再压没有收益，`auto` 会自动跳过，不会越压越大 |
| 文档里全是重复的中文条款 | 压缩器 `max` | 多组 lzma 参数逐个试，压得最狠（但最慢） |

## 预设

| 预设 | 编码器 | 压缩 | 说明 |
|---|---|---|---|
| `chars` | cjk | max | **字符数最少**，冲万字级目标用这个 |
| `compact` | base91 | auto | ASCII 体积最小 |
| `safe` | base32 | auto | 纯大写字母+数字，邮件/IM/Excel 粘贴不会被转义 |
| `fast` | base64 | zlib | 速度优先 |
| `plain` | base64 | none | 不压缩，最透明 |
| `自定义` | 手动 | 手动 | 改下面任意一项，预设会自动变成「自定义」 |

## 编码器与压缩器

编码器（膨胀率 = 文本字符数 / 原始字节数）：

| 编码器 | 字符/字节 | 特点 |
|---|---|---|
| `cjk` | **0.571×** | 汉字编码（每 14 bit 一个汉字），**字符数最少**，比 base91 再少 54% |
| `base91` | 1.231× | ASCII 下最紧凑，字母表已排除 `-` `'` `\` |
| `base85` | 1.250× | 紧凑，但含 `"` `'` `\`，部分渠道会转义 |
| `base64` | 1.334× | 最通用 |
| `base32` | 1.600× | 纯大写+数字，最耐复制粘贴 |
| `hex` | 2.000× | 最直观可审计 |
| `custom` | 1.334× | 自定义 64 字符码表（`--alphabet`），带码表置换 |

压缩器：`max`（多组 lzma 参数逐个试，取最小）/ `auto`（试 lzma，无收益自动跳过）/ `lzma` / `zlib` / `bz2` / `none`。

## 万字级目标与分段

> 下面的示例用 `python -m officepack` 表示命令；如果你用的是 exe，换成 `dist\officepack\officepack.exe`。

```bash
# 默认整份输出，不分片
python -m officepack pack 报告.docx --preset chars

# 目标：整份文档的文本总量压到 1 万字以内
python -m officepack pack 报告.docx --preset chars --target 10000

# 需要切段时才显式开启：每段最多 1 万字
python -m officepack pack 报告.docx --preset chars --split 10000 --password 123456

# 强制整份输出，覆盖已有的分段设置
python -m officepack pack 报告.docx --preset chars --split 10000 --no-split
```

**是否分片是显式开关**：

| 场景 | 做法 |
|---|---|
| 不分片（默认） | 什么都不加；或加 `--no-split` 强制覆盖 |
| 按字符数切 | `--split N` |
| 切成固定段数 | `--parts K` |

图形界面里对应右侧的「分片输出」复选框：**默认不勾**，勾选后才能填「字/段」，切到还原模式时自动置灰。

**1 万字能装多少，取决于文档的信息量**（1 个汉字承载 14 bit，1 万字 ≈ 17.5KB 不可压缩数据）：

| 文档类型 | 原始大小 | 结果 |
|---|---|---|
| 纯中文正文 4,000 条 | 311 KB | ✓ 1,120 字 |
| 高度重复文本 | 630 KB | ✓ 131 字 |
| 随机二进制 | 8 KB | ✓ 4,572 字 |
| 随机二进制 | 17.5 KB | ✓ 10,000 字（正好上限） |
| 随机二进制 | 50 KB | ✗ 需 28,572 字 = 2.9 段 |
| 含 500KB 图片的 docx | 500 KB | ✗ 需 28.6 段 |

**结论**：纯文字类文档几乎都能进 1 万字；含图片/嵌入对象的文档，图片本身已是压缩格式，无损还原下无法再压，只能分段。

分段格式（每段可独立发送，乱序收集也能拼回）：

```
#OPK1 cae6c6 003/012 l).)@ 9282
<该段载荷，每行 100 字符>
```

头部字段：文档 ID / 序号 / 总段数 / 段 CRC32 / 段字符数。
最后一位让解析器精确截断——**段尾多粘了无关文字会被自动忽略**，不会破坏校验。

还原时把全部段一起传入即可（顺序随意）：

```bash
# 从文件还原，分片可一次给多个
python -m officepack unpack part*.txt --password 123456

# 不用存文件：把分片文本从管道喂进去
type part*.txt | officepack.exe unpack - --password 123456
```

**手动输入文本还原**：图形界面右侧有 **「粘贴文本还原…」** 按钮，把容器文本直接粘进文本框即可，
不用先存成文件。支持三种形态：

- 一整个完整容器
- 单个分片
- **多个分片全粘在同一个文本框里**，顺序随意，段与段之间夹说明文字也不影响

对话框里有「检查分片」，会实时显示 `共 24 段，已收 5 段，缺第 6、7、8…段`，
凑齐了再点「还原」，避免白试一次。

缺段、重复段、单段被改动，都会明确报错并指出是第几段。

实测（含 1.5MB 图片的 docx，1,500,594 字节）：

| 方案 | 文本体积 |
|---|---|
| base32 + zlib | 2,426,278 B |
| base64 + zlib | 2,022,016 B |
| base85 + lzma | 1,895,329 B |
| **base91 + auto** | **1,864,514 B**（比 base32 省 23%） |

未压缩的文本型 doc（1,260,000 字节）：`base32+zlib` → 5,659 B，`base91+auto` → **1,066 B**（省 81%）。

## 运行环境（Python 版本）

**用 exe 的话，机器上不需要 Python。** 打成 exe 时已经把 Python 3.14 运行时 +
全部依赖（Pillow / cryptography / qrcode / zxing-cpp）一起封进去了，
目标机器只要 Windows 10/11 64 位、双击就能跑。

从源码跑才需要 Python，要求与依赖一致：

| 组件 | 要求 |
|---|---|
| Python | **3.8 或更高**（Pillow ≥ 10 起的门槛；3.7 装不了 Pillow 10） |
| Pillow | ≥ 10.0（二维码出图、GIF、截图） |
| cryptography | ≥ 41.0（只加密时需要） |
| qrcode | ≥ 8.0（二维码出图） |
| zxing-cpp | ≥ 2.2（二维码识别） |
| tkinterdnd2 | 可选，装了才能拖拽文件 |

代码本身没有用 3.9+ 的语法或运行库特性，所以 3.8 能跑；但**更高版本更省心**——
项目全程在 **Python 3.14** 上开发和验证（91 项测试 + exe 就是用 3.14 打的）。
3.13 / 3.14 不存在「太新跑不了」的问题。

> 常见误解：`from __future__ import annotations` 让所有类型注解都变成字符串，
> 所以 `list[str]` / `str | None` 这种写法在 3.8 上也不会报错。

## 二维码通道

文本之外，也可以把文件做成**二维码图片**：走扫码工具（AirScan-QR、鹊桥之类）跨网传输，
或者干脆截图再扫回来。还原依旧是逐字节一致。

```bash
# 打包成二维码：一张放不下会自动拆成多帧
python -m officepack pack 报告.docx --qr

# 想尽量一张搞定 —— 用二维码专用预设（qr45 + lzma max）
python -m officepack pack 报告.docx --qr --preset qr

# 额外输出循环播放的 GIF 动图（手机对着屏幕扫）

```

> **WebP 合成快不快？** 几百帧的无损动图 WebP 要压几十秒（983 帧实测 24~44 秒，
> 日志里会写「合成 WebP 用了 N 秒」）。libwebp 的**无损**编码器是单线程的，
> `threads` 参数对它无效（实测 ±5% 噪声），所以提速靠四件确定有效的事：
> ① 界面上「**WebP 设置**」选「速度」——每帧约 25ms、体积大约四成，选「体积」则每帧约
> 45ms、体积最小（两种都是无损，扫出来完全一样）；
> ② 编码档位按帧数自适应（小文件省体积、大文件砍一半时间）；
> ③ 同时要 GIF + WebP 时帧只渲染一遍；④ 只选 WebP 时不再白画一遍 PNG。

### 一张码能装多少（物理上限）

二维码 v40 在**字母数字模式**下的容量（字符）：

| 纠错级别 | 容量 | 说明 |
|---|---|---|
| **L** | 4,296 | 默认。容量最大，屏幕截图场景够用 |
| M | 3,391 | 有轻微污损/缩放时更稳 |
| Q | 2,420 | 打印后拍照、折痕场景 |
| H | 1,852 | 最耐污损，容量最小 |

上限就是这样：4,296 字符 × 5.5 bit ÷ 8 = **2,953 字节**，任何编码都突破不了。

`--preset qr` 用的是 `qr45` 编码器（2 字节 → 3 字符，字符集是二维码的 44 个字母数字符号），
比 `base32`（1.6 字符/字节）少占 6.7%，是这份容量里能榨出的最后一点。实测单张上限：

| 场景 | 单张码最大装多少（压缩后） |
|---|---|
| 不加密 + `qr45` + L | **2,495 字节** |
| AES-256-GCM 加密 + `qr45` + L | **2,357 字节** |
| 同上但用 `base32` | 2,077 字节（v1.2 之前的口径） |

编码器对帧数的影响很大，**用默认的 `cjk` 出码会多出 4.7 倍帧数**：

| 编码器 | 每字符占 bit | 相对 `qr45` 的帧数 | 什么情况下值得用 |
|---|---|---|---|
| `qr45` | 5.5（字母数字模式） | 1.0× | **二维码一律选这个** |
| `base32` / `hex` | 5.5（字母数字模式） | 1.07× / 1.33× | 要人能念出来时用 base32 |
| `base91` / `base64` / `base85` | 8.0（字节模式） | ≈1.4× | 想让文本本身更短、且不走二维码 |
| `cjk` | 24.0（UTF-8 汉字） | ≈4.7× | 追求字符数时用，二维码里最费 |

按 2.4 KB 单张上限估算：

| 文件 | 压缩后 | 帧数 |
|---|---|---|
| 3 KB 源码 / Markdown | ~1.4 KB | **1 张** |
| 8 KB 源码 | ~3 KB | 2 张 |
| 21 KB Markdown（本 README） | 9.2 KB | 4 张 |
| 103 KB 的 `python.exe` | 50 KB | 19 张（3 页总览图） |
| 2 KB 的 docx | 1.4 KB | **1 张** |

> 一句话：**压缩后 2.4 KB 以内才能一张搞定**。文本/源码类大约对应 8~12 KB 的原文件；
> docx/zip/pdf 本身已压缩，差不多 1:1，所以只有 2 KB 出头的小文档能单码。

### 静态还是动态

两种都能出，界面上可选：

| 格式 | 适合 | 怎么读 |
|---|---|---|
| **PNG 单帧 + 总览图** | 电脑上还原 | 总览图一张图里有多张码，`unpack` 一次全部识别；也可框选屏幕 |
| **PNG 仅总览** | 不想收一堆 PNG | 只留总览图。总览里的每张码是**原尺寸拼贴、没有任何缩放**，一帧的信息和单帧图完全相同，识别总览就等于识别单帧 |
| **GIF 动图** | 手机扫 / 电脑框选 | 循环播放，相机逐帧抓；**首尾带标识帧**（见下节），框选时能判断一轮起止；也能把 `.gif` 当文件直接丢给 `unpack` |
| **PNG + GIF** | 不确定用哪端 | 两套都出 |

GIF 对二维码是**无损**的：只有黑白两色，2 色调色板 + LZW 不做任何量化。
所有帧统一成**同一像素尺寸**（按最大的那帧算模块大小、其余居中补白）—— 尺寸不一致时
GIF 逻辑画布按首帧走，比画布大的帧会被裁掉右/下边，播放器里就是个残缺码，
怎么扫都扫不出来（1.4.1 修的真 bug）。
但体积不会比 PNG 更小 —— 各帧图案完全不同，GIF 的帧间压缩用不上：

| 输出（4 帧，960px） | 体积 |
|---|---|
| 4 张单帧 PNG | 69 KB |
| 1 张总览图 PNG | 72 KB |
| 1 张 GIF | 131 KB |

想压体积就**降分辨率**：二维码识别看的是「每模块几个像素」，3 px 就够（v40 是 185 模块，
555 px 即可），不必 5 px。`--qr-px 600` 能省 30%~40%，识别率不受影响。

### 出码和扫码有多快

二维码只有黑白两色，但一帧就是 177×177 个模块，出码本质上是「生成 3 万多个格子的矩阵」。
1.4.1 之前用的是纯 Python 的 `qrcode`，生成一张 QR 40 版矩阵要 **275~350 ms**，
再放大成图，单帧 720 ms —— 1 MB 文件 451 帧要跑 **5 分钟**，界面上什么都看不出来。

1.4.2 换掉了三处（都是**没有新增任何依赖**的换法）：

| 环节 | 换法 | 效果 |
|---|---|---|
| 生成矩阵 | 改用打包里本来就有的 `zxing-cpp`（C++ 写码，`create_barcode`） | 720 ms/帧 → **15 ms/帧** |
| 存 PNG | 图改成 L 模式（1 字节/像素）+ `compress_level=6`，写盘交给线程池 | 68 ms → **0.9 ms/帧** |
| GIF 调色板 | 固定双色调色板替掉 `ADAPTIVE` 量化（黑白图两者逐像素一致） | 27.9 ms → **1.1 ms/帧** |
| 扫码 | 动图**并行快扫**（zxing 放 GIL），只对空手的帧回头深挖 | 161 s → **4 s** |

实测同一份 348 KB 文件（129 帧）：

| 阶段 | 1.4.1 | 1.4.2 |
|---|---|---|
| 渲染 129 张 PNG | ~85 s | **8.0 s** |
| 合成 GIF（131 帧） | **92.6 s** | **3.0 s** |
| 识别整个 GIF（129 帧） | **161 s** | **4.0 s** |
| 识别 129 张 PNG（并行） | ~40 s | **10.4 s** |

> 老版本扫一张 129 帧的动图要 2 分 41 秒 —— 「点了没反应、以为卡死」就是这么来的。
> 现在同样的图 4 秒出结果，界面上还有实时进度条。

### 1.4.6：2MB 文件从 5 分钟压到 1 分钟

应用图标在 `assets/officepack.ico`（8 个尺寸，16~256 每个尺寸单独绘制，不是缩图），
由 `python scripts/make_icon.py` 生成；窗口和任务栏都用它。

先把账算清楚。2 MB 文件 = **743 帧**（qr45 + 纠错 L，单帧 2823 字节），
整条链路的实测耗时是这样的：

| 阶段 | 耗时 | 占整份的比例 |
|---|---|---|
| 渲染 743 张码 | 6 秒 | 2% |
| 合成 GIF | 10 秒 | 4% |
| **动图播放一轮**（3 帧/秒） | **248 秒** | **83%** |
| 识别 | 原来每枪 46ms，跟不上播放 | 才是真瓶颈 |

所以「5 分钟」里 4 分钟是**在等动图播完**，不是程序算得慢。两条路一起走：

**一、让识别快到不用等（每枪 46ms → 22ms）**

| 项 | 改法 | 效果 |
|---|---|---|
| zxing 解码 | 只找 QR（`formats=QRCode`） | 46ms → **9ms** |
| 连拍解码 | 再关掉「试旋转 / 试反色」（屏幕上的码永远正着、不反色） | 9ms → **5.6ms** |
| 画面指纹 | 先缩到 48×48 再算哈希（原来哈希 3.4MB 原始像素） | 15ms → **0.55ms** |
| 一枪合计 | 抓图 16.6 + 指纹 0.55 + 解码 5.1 | **约 22ms → 45 枪/秒** |

**二、把播放帧率放开（默认 3 → 10，上限 20）**

| 帧率 | 743 帧播一轮 | 加上生成 25 秒 | 合计 |
|---|---|---|---|
| 3 帧/秒（旧默认） | 248 秒 | 264 秒 | **4 分 24 秒** |
| 10 帧/秒（新默认） | 74 秒 | 90 秒 | **1 分 30 秒** |
| 15 帧/秒 | 50 秒 | 66 秒 | **1 分 06 秒** |
| 20 帧/秒（上限） | 37 秒 | 53 秒 | **53 秒** |

> 20 帧/秒是算出来的上限：一枪 22ms（45 枪/秒），20 帧/秒时每帧还能采到 2.2 次；
> 再高就接近 1 次，漏一枪就少一帧。GIF 的延时单位是 10ms，20 帧/秒 = 5 个单位，
> 不会被播放器取整掉。

真机验证（Tk 窗口按 10 帧/秒换帧 → GDI 抓真屏 → 连拍）：
**122 帧的动图 14.3 秒收全 120/120，一帧不差**。同一份用 15 帧/秒跑时，Tk 自己
换帧跟不上（实测只跑到 8 帧/秒），日志里会写「实测收帧 8.1 帧/秒（设定 15）：
播放器跟不上」—— 卡在播放器还是卡在识别，一眼能看出来。

> **为什么默认不是「一帧塞 4/9 张码」？** 那样播放时间能除以 4 或 9，但每张码的
> 模块数不变、屏幕上的面积只有 1/4、1/9，看图软件一缩放就掉到 2 像素/模块以下。
> 所以它是个**可选**档位（`--qr-matrix` / 界面下拉框），屏幕够大时再往上开 ——
> 详见 [1.4.7](#147一帧放-9-张码动图帧数砍到-19扫描再快-5-倍)。

### 1.4.7：一帧放 9 张码，动图帧数砍到 1/9

动图慢在「等它播完」，而播放时长 = 帧数 ÷ 帧率。帧率有上限（播放器跟不上、每帧
还得采到两次），能砍的只剩**帧数**：把 N×N 张码先拼成一张大图，再拿大图合成动图。

| 矩阵 | 9 帧数据 → 动图帧数 | 单张尺寸 | 播一轮（10 帧/秒） | 屏幕要显示到 |
|---|---|---|---|---|
| 1×1 | 11 帧 | 740×740 | 1.1 秒 | 约 700px（4.0px/模块） |
| 2×2 | 3 帧 | 1492×1492 | 0.3 秒 | 约 1000px（2.7px/模块） |
| 3×3 | 2 帧 | 2244×2244 | 0.2 秒 | 约 1250px（2.2px/模块） |

743 帧的 2MB 文件按 10 帧/秒：1×1 要 74 秒，2×2 降到 19 秒，**3×3 只要 8 秒**。

识别端什么都不用配，但大图不能整张丢给 zxing —— 它要先做一次全图连通域分析，
图越大越亏：

| 方式（3×3，2244²） | 耗时 |
|---|---|
| 整图一次 zxing | 148ms |
| 切 9 块、2 线程 | 53ms |
| **切 9 块、4 线程** | **30ms** |
| 缩到 1200px 显示（真实看到的尺寸） | **9ms** |

**切在哪是关键**。等分九宫格在「图里只有动图本身」时没问题，真实截图外面还有桌面
和窗口留白，等分就会把码切歪。所以先花 0.6ms 把图压成「每列平均亮度」和「每行平均
亮度」两条投影，靠**贯穿整列/整行的白缝**找真实格子边界再切，每块两侧各留 6% 余量。
二维码内部再白也白不满一整列（定位符和时序图案保证约一半是黑的），判据很稳：

| 场景 | 白缝判定 | 结果 |
|---|---|---|
| 3×3 原始图 | (3,3) | 30.7ms 解出 9/9 |
| 3×3 缩到 1200px 显示 | (3,3) | 9.0ms 解出 9/9 |
| 3×3 贴到灰底桌面（2484²） | (3,3) | 169ms 解出 9/9 |
| 整屏截图只有一张码（1920×1040） | (1,1) | 不走切块，正常识别 |

两重保险：行列判定不一致（水印、半透明蒙层会数岔）就当单码帧处理；切块后一张都认
不出来，一律退回整图识别 —— 宁可慢，不能漏。

```bash
# 一帧拼 3×3（9 张码），9 帧的文件只出 2 帧动图
python -m officepack pack 报告.docx --qr --preset qr --qr-gif 10 --qr-matrix 3
```

界面里是二维码那一行末尾的下拉框：`1×1 / 2×2 / 3×3`，默认 `1×1`。


### 1.4.8：抓屏提速（GPU 自适应 + 抓解分离），以及「为什么不做视频」

用户提了个很自然的问题：**动图帧率上不去，能不能改用 30 帧/秒的视频？**

先量了体积 —— 不是障碍：H.264 有损全 I 帧每帧 12~13KB，和 GIF 一个量级（743 帧约 9MB），
二维码是二值图，CRF 28 都能 169/169 全解出来。顺带一个反直觉：**HEVC 反而大 3.5 倍**
（全是噪声样的高熵纹理，x265 帧内编码不擅长这个）。

真正否掉它的是**采样节奏**。用 Chrome 真播 + 本工具真抓屏，连拍 4 秒：

| 播放载体 | 收到 | 有效数据帧/秒 |
|---|---|---|
| **GIF 10 帧/秒** | **19/19 矩阵帧全收** | **27.9** |
| GIF 20 帧/秒 | 19/19 | 27.8 |
| WebP 20 帧/秒 | 16/19 | 23.4 |
| MP4（H.264 30 帧/秒） | 14/19 | **20.5** |

一枪要 30~120ms，视频 33ms 换一帧，抓到的常常是「半新半旧」的撕裂帧 —— 所以
**MP4 是四种里最慢的**。而且 10 → 20 帧/秒毫无变化（27.9 对 27.8），说明瓶颈压根
不在播放侧。要输出 MP4 得打包 ffmpeg（97MB，单文件版 26MB→55MB），投入和收益反着走。

于是把力气全花在采样上，两处改动：

**① 抓屏按机器自适应**（`officepack/screengrab.py`）

| 方式 | 原理 | 实测 |
|---|---|---|
| GDI BitBlt | 只 BitBlt 框内那块（不是整屏再裁，`ImageGrab` 是整屏） | 16~34ms/枪 |
| DXGI 桌面复制 | 帧本来就在显存里，切框内那块到暂存纹理再 `Map` 读回 | 有独显时通常 2~5ms |

驱动不支持桌面复制时，`DuplicateOutput` 在部分机器上**不是返回错误码而是访问违例**
（本机实测），try/except 拦不住。所以第一次扫描时起一个**子进程**去试
（`--probe-grab`），父进程只看它有没有写出结果文件；结论按显卡名缓存进
`%LOCALAPPDATA%\OfficePack\grab_probe.json`，换显卡/重装驱动自动重判。
软件渲染适配器（Microsoft Basic Render Driver / 虚拟机）会被提前认出来，根本不往下调。

**② 抓屏和结码分离**

`Prefetcher` 把抓屏放到后台线程（只留最新 2 帧），主循环只等解码；解码线程数 4 → 8
（zxing 读码时释放 GIL，多开才有意义）。同一块屏实测 **28 → 48 枪/秒**。

端到端（1920×1200@125%，Intel 核显，169 帧的动图）：

| 矩阵 | 收齐 | 枪/秒 | 数据帧/秒 | 用时 |
|---|---|---|---|---|
| 2×2 | 169/169 | 38.9 | 26.7 | 6.3 秒 |
| 3×3 | 169/169 | 47.7 | **61.5** | **2.7 秒** |

**③ 矩阵尺寸把账算给用户看**

3×3 的限制不是「窗口装不装得下」，而是每张码还剩多少像素：单帧约 2900 字节时二维码
是 version 40（177 个模块）。阈值按实测定的（400KB 文件、真实帧按比例缩到各尺寸后解码）：

| 每张码 | 像素/模块 | 结果 |
|---|---|---|
| 720px | 4.1 | 36/36 全中 |
| 420px | 2.4 | 36/36 全中 |
| 350px | 2.0 | 27/27（走整图识别；切块因缝隙被压没而失效） |
| 300px | 1.7 | 26/27，开始掉 |

所以点「开始处理」时会算：

```
· 3×3 原图 2184px，工作区只有 1150px：每张码 383px（2.2 像素/模块，勉强）。
  播放时整个正方形必须完整显示，被任务栏或窗口边切掉一条就是整行码丢失
  —— 用浏览器 F11 全屏最稳。建议改用 2×2（每码约 3.2 像素/模块）会更从容。
```


### 1.4.10：进度不再「0% 挂一分钟」，打包链路提速 3~4 倍

用户报「初始压缩加密一直 0%，60 秒了还是 0%」，紧接着又说「合并也没有进度，只看到 100%
了还要处理 30-40 秒」。三个静默黑洞，全部堵上。

**1. 压缩先说「压不压得动」**

已压缩格式（rar/zip/7z/docx/mp4）再压，压缩率就是 100% —— 但 `max` 档要**全量试 4 组
lzma**，16.5MB 实测 34.6 秒，压完发现「一点没省」，结果全丢。现在先用 256KB 采样
（首/中/尾各一块）花 0.2 秒判断，压不动就直接原样打包：**34.6 秒 → 0.13 秒**。

真能压的数据也不再全量试 4 组，改成「采样选参 → 按最优参数压一次全量」：9MB 文本
2.09 秒 → 0.71 秒，**压缩率一模一样**（采样选出的参数组和全量选出的相同）。

**2. 编码只做一次**

`pack_bytes` 算过一次编码，`build_frames` / `render` / `split_pack` 又各算一次。16.5MB
每多一遍就是 5 秒。现在编码结果跟着 `PackResult` 走，下游直接复用。

**3. WebP 写入改成「逐帧并行 + 自己拼容器」**

PIL 的 `save_all` 走 libwebp 的 `WebPAnimEncoder`：一次性写完、没有中间进度、吃不满多核。
改成每帧独立编码（libwebp 释放 GIL，实测 8 线程 **6.5 倍**）+ 自己拼 RIFF/ANIM/ANMF：

| | 旧 | 新 |
|---|---|---|
| 957 帧写 WebP | 40~85 秒 | **6~7 秒** |
| 进度 | 直接跳 100%，再干等 | 每帧一次 |
| 内存 | 全部帧铺在内存里 | 只留在飞的几帧 |

成品仍是标准 WebP 动画，PIL 读回来逐帧像素比对完全一致。

**4. 六个阶段各有各的百分比**

```
压缩 0→70% → 加密 70→77% → 编码 77→100% → 排版 0→100% → 渲染 0→100% → 写入 0→100%
```

内部刻度（0~1000）只用来换算，界面只显示百分比。换阶段时日志的「每 10% 一行」重新计数，
事后翻日志就能看出每一步花了多久。

**顺带修掉三个 bug**

- 心跳每秒拿 `done/total` 重写文案，正好把「写入 GIF…大约还要 20 秒」覆盖成「100%」——
  这就是「100% 还要等三十秒」的直接原因。现在一次性写入走动画条 + 估时，心跳只更新秒数。
- 工作线程直接碰 Tk（`_start_bar()`、`webp_mode.get()`），主线程不在 mainloop 时会抛
  `main thread is not in main loop`。现在值在主线程取好再传进去，归零动作走队列派回来。
- `_poll_queue` 里 `_set_bar` 抛一次异常，`after` 就不再续期 —— 之后所有日志和进度
  全部石沉大海。现在有兜底，异常只跳过这一帧。

**5. 图标丢了（again）**

打包命令换成统一脚本后，`--icon` 和 `--add-data assets` 漏了：exe 退回 PyInstaller 默认图标，
窗口/任务栏也没图标（`asset_path()` 在包里找不到 `assets/officepack.ico`）。

两条 GUI 打包命令都补上了，`verify_release.py` 也新增硬校验 —— 包里没 ico 或尺寸 PNG
少于 3 张直接判失败（`11/11 PASS`）。注意 `--specpath build` 时这些相对路径按 build 目录解析，
要写 `../assets`。

**实测**

| 数据 | 帧数 | 旧 | 新 |
|---|---|---|---|
| 585 KB 随机（2×2 WebP） | 213 → 54 | ~25 秒 | **4.6 秒** |
| 2.5 MB 随机（2×2 WebP） | 900 → 222 | ~90 秒 | **13.7 秒** |
| 16.5 MB rar（估算） | 3823 → 957 | ~300 秒 | **~85 秒** |

剩下那 85 秒里约 70 秒花在「排版」：zxing 要逐帧编码 3825 张 version-40 二维码，
单核固定成本（实测 8 线程只有 0.94 倍，没有并行价值）。想再快就降帧数 —— 纠错从 M 降到 L
能多装 26%，帧数少两成。

### 1.4.9：进度行不再被裁，矩阵尺寸的账摊开讲

用户报「合成的时候底部还是显示不全」，另外问「3×3 到底要多大的屏」。

**根因是布局在跑的途中长高了。** 底部那行进度（6px 条 + 一行说明）原来是「有活才
pack」，一出现整窗需要的高度就 +28px。窗口此时已经贴在工作区下沿、长不高，Tk 只好
去压别人 —— 表现就是右侧选项区突然冒出滚动条、底部进度行贴着窗口下沿被裁半截。

改法：**那一行固定占位**（`SUB_ROW_H=24`，空闲时只是空白），从启动到收尾布局一模一样。
顺带把日志的下边距并进这行，净代价只有一行日志。

另外按用户要求「进度条可以适当缩短一点」：

- 进度条封顶 **480px**（原来铺满剩下的 690px），余量全给右边文字
- 文字不再用 `width=31`（那是**字符数**）硬框 —— 阶段名一长，「100% (3825/3825)」这种
  最要紧的数字就被裁掉。改成自适应宽度 + 超长自己省略（42 字符）

新测试盯死这三条：切到进度状态时整窗 `reqheight` 不许变、条子不许超封顶、文字控件
不许比文字窄。

**另外四处（同一轮用户反馈）**

1. **补录不再 3 秒就放弃**。判死规则原来不分场景：第一轮 3 秒内一定见到首帧标识
   （`#OPKmark|S`），够用；但补录时画面可能正播在中段，等标识要等半圈 —— 3 秒判死
   等于一点机会都不给，用户看到的就是「3.2 秒 / 0 轮 / 新收 0 帧」。现在续扫按
   「够播一整轮」算（`总帧数 ÷ 帧率 + 10 秒`，上限 240 秒）。顺带把误报改掉：一帧
   没补到时说「这轮没转到缺的那几帧」，不再说「播放器跟不上」。
2. **采样抖动改成算法**。3823 帧里固定缺 340–343、844–847 等几段，补几轮都补不上 ——
   播放周期和采样周期成整比时的典型相位卡死。现在不再是「随机抖 ±25%」（那是靠运气），
   而是以首帧标识 `S` 为相位 0 点、每圈把采样网格按二分序列 `0 → 1/2 → 1/4 → 3/4 …
   平移，R 圈后最大缺口缩到 `1/2^R`；另加每圈 ±2% 的周期抖动打散格点。详见下面
   「采样抖动：每轮挪多少、共几轮」。
3. **「框选屏幕区域」= 重新开始**。它以前也是「接着上次」，拿新文件来框会把老文件的
   帧一起拼进去。现在默认清空上一次的帧和临时抓图；只有「再来一轮 / 重新框选（接着
   收同一份）」才续扫。差一两帧又补不上时，另有「放弃本次识别」按钮（二次确认）。
4. **悬浮条宽度自适应**。原来写死 440px，「已收 3803/3823 帧（本轮 +3803）· 还要
   1 分钟」直接被裁；现在按最长可能出现的文字量一次宽度（只增不减），上限是虚拟
   桌面宽 - 40。顺带修掉「拖透明度时窗口跟着鼠标乱跑」：拖动原本绑在 Toplevel 上，
   而 Tk 的 bindtags 里 Toplevel 是每个子控件的祖先标签，按滑杆等于同时在拖窗口。


### 采样抖动：每轮挪多少、共几轮

「缺帧」不是随机事件，是**算术**。三个量决定一切：

```
N  = 总帧数（段头里写着）
P  = 播放帧率（从收帧时间戳反推：相邻两帧的序号差 ÷ 时间差）
F  = 采样帧率（程序每秒抓几张）
step = P / F           ← 两枪之间画面往前走了几帧
```

**step 是主因**：

| step | 一轮最多收到 | 场景 |
|---|---|---|
| ≤ 1 | 全部 | 枪速 ≥ 播放率，一轮就该齐 |
| ≈ 1 | ~全部 | 播放器 10 帧/秒、程序 10 枪/秒；缺的几帧是解码失手 |
| 2 | 一半 | 播放 20 帧/秒、采样 10 枪/秒 |
| 3 | 三分之一 | 每轮都漏**同样**那两帧，补几轮都一样 |

**每轮挪多少**：把采样的 0 点定在「见到首帧标识 `S` 的那一枪」，之后每转一圈把
采样网格整体平移一个相位，按二分序列走：

```
0 → 1/2 → 1/4 → 3/4 → 1/8 → 5/8 → 3/8 → 7/8 …        (van der Corput)
```

每一项都落在**现存最大空隙的正中间**，把最宽那段缺口对半劈开 —— 所以 R 圈之后
最大缺口是 `1/2^R` 齿。确定性的，不靠抽签（随机抖要收齐 N 帧，期望 N·lnN 次）。

实测补 5 轮仍停在 22/24 的情形，是「步长 3.33 让采样点卡在格点上」：加每圈 ±2%
的周期抖动后，第 4 轮就齐。

**共几轮**：`qr.plan_jitter()` 把一齿切成 24 份，逐份模拟「挪过去能多收多少帧」，
取收益最大的那份，一直模拟到收齐 —— 同时给出「下一轮挪多少」和「还要几轮」。

目标是**总耗时最短**，不是轮数最少：

```
补轮耗时 ≈ 轮数 × 一圈时长        （每轮都得走完一圈，缺的帧可能在任何位置）
提枪速耗时 ≈ 一圈时长 × 1.05     （枪速 > 播放率时一轮之内就扫完）
```

所以轮数 ≥ 2 时程序直接建议并**自动**把帧率提到 `P × 1.2`（只升不降，上限 20）：

```
步长 3.33（采样比播放慢），补轮要 3 轮 ≈ 7 秒；
最快是把「动图帧率」提到 12 帧/秒，一轮 ≈ 2 秒就齐，快 2.9 倍
```

一轮就够时（step ≤ 1）反而**不动**你的设置 —— 那时提帧率不会更快。

端到端实测（真实解码 + 模拟播放器，`should_stop` 4 秒掐断一轮）：

| 播放/采样 | 第 1 轮 | 预测 | 实际 |
|---|---|---|---|
| 10 / 5 帧/秒 | 18/24 | 再 1 轮 | 第 2 轮 24/24 ✔ |
| 10 / 3 帧/秒 | 9/24 | 再 3 轮 | 第 2→3→4 轮 24/24 ✔ |

### 框选怎么收动图（首帧开始、尾帧结束）

屏幕上播着动图时，**一张截图只能拿到其中一帧**，靠单次截图必然缺帧。所以框选拖完
松手后不是截一张，而是**对着这块区域连拍**：

- **首尾标识帧**：GIF 首帧是 `#OPKmark|S|<文档ID>|<总帧数>`，尾帧是 `#OPKmark|E|<文档ID>`。
  识别端**见 S 才认为一轮开始、见 E 才认为一轮结束**，不用猜播放相位
- 一轮没收齐？画面继续播，自动接着收下一轮；连续两轮颗粒无收才收工
- 静态码第一枪就齐，立刻返回，不会干等
- 漏掉的帧**再框一次会自动续上**（已收的攒着，不重复、不用从头来）
- 画面没变化的帧直接跳过解码（指纹去重，0.55ms 一次），所以采样能追上 20 帧/秒的播放速度
- 旧动图（没有标识帧）照样能用：退化成「连续 3 秒没有新帧就收工」

实测（7 帧数据 + 首尾标识、3 帧/秒播放、真实屏幕框选）：**2.4 秒收全 7/7，还原逐字节一致**。
1.4.6 又在真机上跑了 122 帧 / 10 帧/秒：**14.3 秒收全 120/120**。

### 多帧怎么收（顺序无关）

每张图都是一个自包含的 `#OPK1` 分段，段头写明 `文档ID / 序号 / 总段数 / CRC`：

- **顺序完全无关**：按段头序号重组，倒着扫、跳着扫都行
- **多张图一起给**：截图、单帧图、总览图混在一起也全部识别后合并（不是只认最后一张）
- 扫重了无害：内容相同的重复帧自动忽略
- 扫花了无害：CRC 不过的帧被丢弃，好帧照样拼得回去
- 少一帧会明确告诉你「缺少第 3 段」；如果同时有坏帧，会提示「重扫这几张」
- 同一序号出现两份**不同**内容（两次打包混在一起）→ 直接报错，绝不瞎猜
- 总览图每页 12 帧，多页自动续（19 帧 = 2 页），截两次图就能全覆盖
- 最终还有整文件 SHA-256 收口，任何一位不对都会报出来

### 屏幕水印 / 软件水印

真正麻烦的不是图片文件自带的痕迹，而是**图片显示在屏幕上时**被叠上去的水印：
公司的屏幕监控水印、看图软件/Office 预览加的半透明角标、远程桌面叠加的会话标记。
框选截图会把这层水印一起截进来，直接识别就会掉帧。

识别时不会只试一次原图，而是自动做一轮**像素级净化**再识别，从便宜的往下试，
捞到新帧就继续、收全就停（单张图总预算 6 秒，绝不卡界面）：

| 顺序 | 处理 | 针对什么 |
|---|---|---|
| 1 | 固定阈值二值化（60/80/100/120 四档） | 半透明浅灰水印：码是纯黑，低阈值把「不够黑」的像素全漂白 |
| 2 | Otsu 自适应阈值 | 整体偏暗/偏亮的截图、压缩噪点 |
| 3 | 反色 | 深底浅码（某些看图软件的反色模式） |
| 4 | R/G/B 单通道 | 彩色水印（蓝底白字），单通道里对比度最高 |
| 5 | 2 倍 / 3 倍放大 | 码在屏幕上被缩得很小，每模块不足 2 px |
| 6 | 中值滤波 | 细线状水印 |
| 7 | 重叠切块（2×2 + 12% 重叠） | 大图局部遮挡、水印整块压在某个角上 |

实测（6 帧总览图，铺满整幅的半透明水印 + JPEG 压缩 + 缩放，括号内为只跑原图的结果）：

| 场景 | 只跑原图 | 自动净化 |
|---|---|---|
| 缩放 70% + 水印 + JPEG85 | 6/6 | 6/6 |
| 缩放 55% + 重水印 + 角标 + JPEG80 | 6/6 | 6/6 |
| 缩放 60% + 蓝色水印 + JPEG75 | 6/6 | 6/6 |
| 缩放 35%（每帧约 290 px） | 5/6 | **6/6** |
| 缩放 30%（每帧约 246 px） | 1/6 | **6/6** |
| 缩放 28%（每帧约 230 px） | 1/6 | **5/6** |
| 0.8 不透明度灰字铺满 | 3/6 | **6/6** |

最后一档 28% 还差一帧、24% 基本认不出来 —— 那是**分辨率物理极限**（v40 是 177 模块，
每模块只剩 1 px），任何算法都无解。这时候把图放大到 100% 再截一张，或者用粘贴面板
逐张补，比死磕算法靠谱。

### 多屏与剪贴板

- **框选铺满所有屏幕**：遮罩按 Windows 的「虚拟桌面」尺寸铺，主屏、副屏、副屏在主屏
  左侧导致的负坐标都覆盖；拖动能跨屏。以前只铺鼠标所在那一块，另一块屏不暗也点不到，
  双屏用户会以为功能坏了。
- **跨屏框选不再错位（125% 缩放必踩）**：物理桌面和 Tk 看到的尺寸不一致时（本机实测
  物理 `3840×1200`，Tk 只说 `3072×960`），框选矩形记的是「逻辑坐标」，而截图取的是
  「物理像素」—— 差 1.25 倍，框在副屏就整体偏到主屏边上，抓到一块空桌面。
  现在按「整屏抓图宽度 ÷ 逻辑桌面宽度」反推缩放比再换算，日志会写明
  `屏幕缩放 125%：框选坐标已按物理像素换算`。进程真拿到 per-monitor DPI 时比值为 1，
  这段换算自动失效，单屏用户无感。
- **框选时主窗口自动让开，但任务栏图标一直在**：主窗口铺得宽，留在屏幕上会压住要圈的码，
  所以框选/扫描期间**最小化**（不是隐藏 —— 隐藏会把任务栏图标一起弄没，中途想回来点
  「停止」都无从下手）。从任务栏点回来时窗口不会被强行再藏掉，而是自动**挪到框外**，
  扫描照常继续；识别完（成功、失败、取消、超时）都会回到原来的位置。
- **框内没验到就整屏兜一次**：框小了、框偏了、码被切掉静区，都会让框内一无所获；
  这时自动整屏再扫一遍，只认 officepack 自己的分段（`#OPK1` / `#OPK2`），
  免得把屏幕上别处的二维码当数据。
- **收帧快 4 倍**：抓图不再用 Pillow（它每次都把整个虚拟桌面抓下来再裁，双屏一枪
  83ms），改用 GDI `BitBlt` 只抓框内那块，**20ms/枪**（逐像素一致）。动图 3 帧/秒时，
  一枪 222ms 会漂到「同一帧抓两次、下一帧没抓到」，降到 82ms 后每帧能采 3~4 次。
- **上限按总帧数自适应**：978 帧按 3 帧/秒播一轮要 326 秒，而旧上限只有 30 秒 ——
  结构上就收不全。收到第一帧后从段头读出总帧数，上限自动放到「够播一整轮」。
- **扫描有悬浮条**：框外角落显示 `已收 631/978 帧 · 还要 1 分 40 秒`，带「主窗口」和
  「停止」两个按钮，自动躲开框选区域；中途想看日志点「主窗口」，想中止随时点「停止」。
  - **可以拖**：按住上面的文字直接拖到任意位置，位置会记住
  - **透明度可调**：右上角滑杆 35%~100%，调完记住；想让它更不挡视线就调淡
  - 记住的位置如果正好压在框上，会临时换到没被框住的角
- **补录只补缺的帧**：缺帧时底部出现两个按钮，已收的帧**一帧都不会重收**
  - 「再来一轮（只补缺的 N 帧，不用重框）」—— 同一块区域直接重扫，不用再拖一次框
  - 「重新框选（框歪了才用，同样只补缺的 N 帧）」—— 换一块区域，已收的照样留着
  - 为什么缺 1 帧也要等一整轮：缺的那帧可能在第 1 帧也可能在最后一帧，只能让动图
    从头播到尾、见到尾帧才敢停。日志会提前写清这一轮大约要多久
  - 换成**另一份文件**时会自动把上一份的帧作废，不会混在一起（按段头里的文档 ID 判断）
- **缺帧只说区间**：`缺 797 帧：第 1–118、209–547、639–978 帧`，
  不再是上千个数字的流水账。
- **识别失败会留下证据**：把最后抓到的画面存成
  `%TEMP%\officepack_框选抓图_<时间>.png`，路径写进日志和提示框 ——
  是码太糊、框错地方还是被窗口挡住，看一眼就知道。
- **剪贴板直读**：不再依赖 Pillow 的 `grabclipboard()` 只认最前面一项；直接读
  `PNG / CF_DIBV5 / CF_DIB / CF_BITMAP / CF_HDROP`，Ditto 放进去的 `CF_DIB` 也能读出来。
- **Ditto 兼容**：自动探测 `Ditto.exe`（运行中的进程 → 卸载注册表 → PATH → 环境变量与
  各本地盘符的常见目录，**不写死任何路径**）。点「打开 Ditto 剪贴板」把历史窗口叫出来，
  在里面双击要用的图，Ditto 会把它贴进面板，自动识别累积。
- 没装 Ditto 就走兜底：`Win+Shift+S` 截一张 → 回面板 `Ctrl+V`，效果一样。

### 识别不到怎么办

1. 让整张码**完整入镜**，四周留白（静区）别裁掉
2. 不要缩小、不要加滤镜/锐化；屏幕截图直接存 PNG 最稳
3. 手机拍屏幕会有摩尔纹，改用截图
4. **码太小**是最常见原因：把图放大到 100% 或全屏再截图；用总览图时尽量让每帧 ≥ 400 px
5. 缺帧时用「粘贴识别面板」逐张补 —— 顺序完全无所谓，缺第几帧会明确告诉你
6. 图太小扫不出来时，降低纠错级别（L）或调小 `--qr-chars` 让每张码更宽松
7. **动图框选**：让它在框里一直循环播放，别停在某一帧；一轮没收齐会自动再等一轮，
   还缺的话再框一次同一块区域即可（已收的会累加，不必从头来）

## 文本容器格式

```
-----BEGIN OFFICEPACK v1-----
Meta: eyJ2IjoxLCJuYW1lIjoi...          ← base64(JSON)：文件名/大小/SHA-256/算法参数
Info: 报表.docx | 48213 B | text=59187 chars | codec=base91 | compress=lzma | cipher=aes-256-gcm
Preview:                                ← 人可读正文预览（不参与还原，可用 --no-preview 关闭）
  | 第一章 总述
Payload:                                ← 纯 ASCII 载荷，每行 100 字符
MZXW6YTBOI...
-----END OFFICEPACK v1-----
```

还原只依赖 `Meta` + `Payload`，`Info` / `Preview` / 注释行全部忽略，
所以文本可以随意加前后缀、被邮件折行、被 IM 截断后拼接回来。

`--ascii-only` 可让整个文件严格 7-bit ASCII（注释区中文转 `\uXXXX`）。

## 安全

- **AES-256-GCM**，密钥由口令经 **scrypt**(n=16384, r=8, p=1) 派生
- 每块独立 nonce（8B 随机前缀 + 4B 计数器），分块 1 MiB，内存占用与文件大小无关
- AAD 绑定原始大小与 SHA-256 → 元信息被改动会导致解密直接失败
- 任意一位翻转都会触发 GCM 认证失败或 SHA-256 校验失败

## 限制

- 老格式 `doc / xls / ppt` 不生成文字预览（无法解析 OLE2），但**无损还原完全支持**
- `cjk` 编码器字符数最少，但 UTF-8 字节数约为原始的 1.71 倍——只适合「按字符数限制」的渠道；
  若渠道限制的是字节数，请用 `base91`
- 打包需全量读入内存，峰值约为文件大小的 3~4 倍；几十 MB 的文档无压力
- 依赖 `cryptography`（仅加密时需要），未安装时可用 `--cipher none`
- **单张二维码最多装 2.4 KB（压缩后）**，这是 QR 标准的物理上限，换编码器也只能多 6.7%。
  所以二维码天然只适合几 KB ~ 几十 KB 的文件；更大文件会拆成很多帧，建议走文本通道
- 二维码通道**不限定编码器**，但 `base91/base64/cjk` 会掉出「字母数字模式」，
  同样内容多占 1.4~4.7 倍帧数；**出码一律用 `--preset qr`**
- GIF 动图无法被 `PIL` 当作静态图一次读全 —— 但本工具的 `unpack` 会逐帧识别，直接给它 `.gif` 即可

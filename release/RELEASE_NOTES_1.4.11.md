# OfficePack 1.4.11 — 中途能停，停完能清，跑完知道你等了多久

这一版回应四个问题，其中两个是「一直想做但没下手」的：

1. **生成/还原过程中生成的动图帧 PNG，到底存哪儿了？会不会一直占着缓存？**
2. **生成过程也该有中止按钮**（以前只有框选扫描能停）
3. **中止之后，过程产生的中间文件应该清掉**（强退时留下的谁来清？）
4. **生成/还原都该显示本次用了多久**，另外给一个手动清理按钮

---

## 一、先回答：动图帧 PNG 根本不落盘

「会不会一直存在缓存里」——不会，而且连磁盘都不碰。实测（20 KB 随机数据 → 8 帧）：

```
=== 输出目录（用户要的产物）===        新增 11 个
   + probe.qr001.png ~ probe.qr008.png   各 14.7 KB
   + probe.qr-all.png                   149.8 KB
   + probe.qr.gif                       271.6 KB
   + probe.qr.webp                       52.0 KB

=== 系统临时目录 %TEMP% ===            新增 0 个
峰值内存：4.4 MB
```

机制上分三类，处理方式完全不同：

| 东西 | 在哪儿 | 谁会清 |
|---|---|---|
| **动图帧**（一帧一张二维码图） | 只在内存里，逐帧产出、用完即弃（流式生成器） | 出下一帧时自动释放，没有残留 |
| **产物**（`.qr001.png` / `.gif` / `.webp` / 总览图） | 输出目录 | **不自动删** —— 那是你要的东西 |
| **诊断抓图**（识别失败时存的那张屏幕截图） | `%TEMP%\officepack_框选抓图_*.png`，一张约 200 KB | 启动时清隔夜的；中止和手动清理按钮会清当次的 |

唯一的例外是「同时要 GIF 和 WebP」：PIL 的 GIF 必须拿到完整帧列表，这时两种动图共用一份全量帧，会在函数返回前一直驻留内存（几百帧的大图可能几百 MB）。只要选一种格式，就始终是流式的。

## 二、中止按钮：六个阶段全设了检查点

以前只有「框选扫描」有停止按钮，打包和还原一旦开跑就只能等：957 帧的动图要跑一分钟，中途发现格式选错了也停不下来。

现在「开始处理」右边就是「中止」。它不是「发给线程一个标志位然后等它自己发现」，每个阶段都在**帧边界**查一次：

| 阶段 | 检查点位置 | 中止时手上这一帧 |
|---|---|---|
| 压缩加密 | 分块流式压缩的块边界 | 做完当前块 |
| 编码 | 按 2/3/5/1 字节对齐的分组边界 | 做完当前组 |
| 排版（zxing 预排） | 每帧（3825 帧这里要跑一分钟，最需要能停） | 做完当前帧 |
| 渲染 | 每出一帧 | 出完当前帧 |
| 编码成 WebP | 每帧（并行池里在飞的最多 16 帧） | 收完在飞的 |
| 写盘 | 写之前 | —— |

实测**点下「中止」到界面回到可操作状态：0.6 秒**（165 帧的任务，0.6 秒时点，1.2 秒全部结束）。

### 中止不会删你已经写出来的文件

这一点想清楚了才动手：中止发生在渲染阶段时，磁盘上可能已经有几十张单帧 PNG，那些是**能直接用的半套码**，删掉才是损失。所以中止只做三件事：

1. 停下后面的活；
2. 清掉中间文件（诊断抓图）；
3. 如实告诉你「已写出 N 个文件，保留在原处」，并问要不要打开那个目录。

> 修了一个会误导人的 bug：逐张写 PNG 时异常是从写盘循环里抛的，调用方手上的返回值是空的，于是收尾提示会说成「没有写出任何文件」——而用户打开目录能看到 13 张图。现在中止会把「已落盘的文件」随异常带出来（`Cancelled.partial`），提示与实际对齐。

## 三、本次总用时

- 日志收尾行：`── 完成：成功 1 / 失败 0 · 本次用时 7.7 秒 ──`
- 完成弹窗：`本次用时：7.7 秒`
- 每个文件单独一行：`本文件用时 7.7 秒`（多文件时能看出是哪个拖慢的）

同一份文件换压缩档、换矩阵、换 WebP 档位到底快了多少，以前只能靠感觉，现在有数了。

## 四、「清理临时文件」按钮

在左下角（「清空」右边）。清的是 `%TEMP%` 里本程序自己写的东西：

- 框选识别失败时的诊断抓图（`officepack_框选抓图_*.png`）
- 点一次报告「清理了 N 个，释放 X MB」

**为什么需要手动按钮**：程序被强杀（任务管理器结束进程、断电、蓝屏）时，收尾代码根本没机会跑，这些图就永久留在临时目录里——攒几十次能到上百兆。启动时虽然会清「隔夜的」，但当次强退留下的清不到。给个按钮，用户才能一次清干净。

## 五、修掉的另一个小毛病

中止后日志末尾会冒出一行旧进度（`渲染 PNG 12%（19/152）`），看着像中止没生效。原因是主线程一次轮询里读到 `done` 就收尾了，但循环末尾还会把同一批里读到的最后一条进度再刷一帧。现在收尾时把积压的进度消息直接作废。

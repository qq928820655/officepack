# v1.4.2 — 出码快 30 倍、扫码快 40 倍，全程有进度

> 一句话：**大文件不再「点了没反应」。** 129 帧的动图，出码从 92 秒降到 3 秒，
> 识别从 2 分 41 秒降到 4 秒；界面上多了一条**当前文件内部的进度条**，
> 日志每 10% 留一行，一秒一跳心跳。

## 1. 慢在哪：三处纯 Python / 重复劳动

二维码一帧是 177×177 个模块，出码本质上是「生成 3 万多个格子的矩阵」。
1.4.1 之前用的是纯 Python 的 `qrcode`：

| 环节 | 1.4.1 | 1.4.2 | 怎么改的 |
|---|---|---|---|
| 生成矩阵 | 275~350 ms/帧 | — | 改用打包里本来就有的 `zxing-cpp`（C++，`create_barcode`） |
| 单帧渲染总耗时 | **720 ms** | **15 ms** | 上面这条的直接结果（快 48 倍） |
| 存 PNG | 68 ms/帧 | 0.9 ms/帧 | 图改 L 模式（1 字节/像素）+ `compress_level=6`，写盘进线程池 |
| GIF 调色板 | 27.9 ms/帧 | 1.1 ms/帧 | 固定双色调色板替掉 `ADAPTIVE` 量化（黑白图两者逐像素一致） |
| 扫码（逐帧） | 65.9 ms/帧 | 27.0 ms/帧 | 动图并行快扫（`read_barcodes` 放 GIL，4 线程 2.4 倍） |

**没有新增任何依赖** —— `zxing-cpp` 本来就是识别端的依赖，打包里已经有了。
`qrcode` 保留为退路：万一 `zxing-cpp` 版本太老没有写码能力，自动切回去。

### 实测（348 KB 文件，129 帧）

| 阶段 | 1.4.1 | 1.4.2 |
|---|---|---|
| 渲染 129 张 PNG | ~85 s | **8.0 s** |
| 合成 GIF（131 帧） | **92.6 s** | **3.0 s** |
| 识别整个 GIF（129 帧） | **161 s** | **4.0 s** |
| 识别 129 张 PNG（并行） | ~40 s | **10.4 s** |

## 2. 扫码慢的真凶：每帧都白跑 6 秒重试

`_read_one` 的深度重试逻辑是「原图读不全就换各种像素变换再试，最多 6 秒」。
问题在于动图是**逐帧**调用它的，而每一帧里只有 1 个码、永远「不全」——
于是 129 帧每一帧都老老实实把整套重试跑一遍，实测 **1.1 秒/帧**。

现在改成两轮：

1. 先**并行快扫**每一帧的原图（一次像素变换都不做，几十毫秒一帧）
2. 只有确实一个码都没读到的帧，才回头做深度重试（最多 8 帧）

129 帧的动图 161 秒 → 4 秒。**「点了没反应」的大部分其实是这个**。

## 3. 界面上现在能看到进度了

- **二级进度条**：上面一条是「第几个文件」，下面一条是当前文件内部走到哪了
  —— `渲染 PNG 45% (58/129) · 3.2s`
- **日志每 10% 留一行**，事后翻日志能看出哪一步花了多久
- **一秒一跳心跳**：长任务里进度不动时，至少让人看出还在跑，不是死了
- 命令行同样有进度：`｜█████████·····｜ 45% (58/129)`，原地覆写不刷屏

## 4. GIF 调色板：一个被顺手堵住的坑

GIF 用 `disposal=2`（每帧先清成背景色再画差异区域），而**背景色取的是调色板 0 号**。
老实现靠 `ADAPTIVE` 量化「碰巧」让 0 号是白；这次换成固定调色板，如果 0 号写成黑，
有些播放器就会把整屏刷黑再叠差异 —— 画面成了满屏噪点，肉眼和扫码器都认不出。

现在显式保证 0 号 = 白，并加了断言防回归。

## 5. 识别端补了两条

- **静区补白变体**：截图/框选把四周静区切掉了，是最常见的「怎么扫都扫不出」之一。
  现在会先把图四周补白再试一次，实测切掉 16 px 静区的码立刻能读回来。
- **失败信息更具体**：会告诉你「其中 xxx.gif 是 131 帧的动图」，并提示如果是旧版
  生成的动图请重新生成（旧版每帧尺寸不一，GIF 会把大帧裁掉右/下边）。

## 升级建议

**旧版生成的 GIF 建议重新生成一次。** 1.4.1 修掉了裁边 bug，但已经生成的旧文件
还是残缺的；新版出码快了 30 倍，重新生成 129 帧只要 3 秒。

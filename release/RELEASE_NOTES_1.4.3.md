# v1.4.3 — 修好「副屏框选识别不了」，外加无损 WebP 动图

## 一句话

**主屏放程序、副屏放二维码，框选永远识别不了** —— 根因不是识别能力，是**坐标系差 1.25 倍**。
这一版修掉了，顺带把框选体验补齐，并新增体积只有 GIF 五分之一的**无损动图 WebP**。

## 一、跨屏框选识别不了（真 bug，已修）

### 现场

> 同一个屏幕识别正常，但应用在屏幕 A、二维码图片在屏幕 B，框选 B 上的码依旧不行。

日志只有一行结论，看不出原因：

```
✗ 框选区域没识别到二维码：1.3 秒 / 6 枪
```

而那张码本身完全没问题 —— 把当时的整屏截图拿出来单独识别，一读就中。
**问题不在码，在「框到的是哪儿」。**

### 根因：逻辑坐标 vs 物理像素

在本机实测（125% 缩放、双屏）：

| 谁在说 | 说桌面有多大 |
|---|---|
| 物理分辨率（`ImageGrab` 抓到的图） | **3840 × 1200** |
| Tk / `GetSystemMetrics`（程序拿到的坐标） | **3072 × 960** |

Tk 给的是**逻辑坐标**，截图取的是**物理像素**，差 **1.25 倍**。于是框在副屏、
逻辑上 `x=1536` 起的那块，被送到截图 API 后仍然按 `1536` 去裁 —— 裁到的是主屏右半边的**空桌面**。

单屏时误差落在屏幕边界之外，不容易被发现；一跨屏就必现。

### 实测对比（真机、真码、副屏显示）

```
旧（逻辑坐标直接抓）  bbox=(1596, 80, 2296, 780)   抓图 700×700  → ❌ 没识别到
新（按 scale 换算）    bbox=(1995, 100, 2870, 975)  抓图 875×875  → ✅ 识别到 1 个码
```

### 修法

不再依赖「进程有没有拿到 per-monitor DPI」，而是**用事实反推**：整屏抓一张，
`缩放比 = 抓图宽度 ÷ 逻辑桌面宽度`，把框选矩形换算成物理像素再截。日志会写明：

```
· 屏幕缩放 125%：框选坐标已按物理像素换算（这就是「一块屏能识别、换块屏框不准」的根因）
```

- 进程真拿到了 per-monitor DPI 时，两个数本来就相等，比值 1.0，换算自动失效 —— **单屏用户无感**
- 不再赌 Tk 的坐标换算，也不赌 `GetCursorPos`（系统 DPI 虚拟化下它同样是逻辑坐标）

## 二、框选时主窗口自动让开

主窗口铺得宽，留在屏幕上会正好压住要圈的码。现在框选期间自动隐藏，
**成功 / 失败 / 右键取消 / Esc / 10 秒超时兜底** 全都会把窗口放回来。

## 三、框内一无所获时，整屏兜一次

框小了、框偏了、静区被切掉一角、码被别的窗口压了一半 —— 都会让框内扫描空手而归。
这种情况下自动**整屏再扫一遍**，并且只认 officepack 自己的分段（`#OPK1` / `#OPK2`），
不会把屏幕上别处的二维码当成数据。

## 四、识别失败会留下证据

以前「识别不了」只有一句话，谁也没法定位。现在会把最后抓到的画面存成

```
%TEMP%\officepack_框选抓图_<时间>.png
```

路径同时写进日志和提示框 —— 是码太糊、框错地方、还是被窗口挡住，**看一眼就知道**，
也能直接把它拖进文件列表试试，判断是不是图本身的问题。

## 五、静态图会明说「补不齐」

框到的是**照片/截图里的一张码**（帧号显示 `071/978` 这种），静态图里永远只有 1 帧，
再怎么框也补不齐。以前只会反复提示「再框一次」；现在直接告诉你换路子：

- 要传整份文件：出码时选 `PNG + GIF`，让 GIF 在屏幕上循环播放再框
- 手上只有 PNG：把**总览图**直接拖进文件列表识别，总览里一格就是一帧

顺带把「一枪都没见着就收工」的阈值从 6 枪提到 **10 枪**（约 2 秒）——
整屏抓图 + 解码一枪要 0.2 秒，1.3 秒就判死刑太急，屏幕刚好在刷新/滚动就白判了。

## 五之二、修好之后又暴露一个：裸读失手 = 永久漏帧

修完坐标，真机跑通了，但第一次仍然要 **10 枪 / 1.9 秒** 才出结果。查下来是第二个坑：

- 屏幕 125% 缩放下，码是被**双线性拉伸**过的，`fast` 裸读（只跑原图一次）经常差一口气；
- 而画面不变时 `_frame_key` 会跳过解码 —— **第一枪失手，后面每一枪都不会再看它**，
  等于这一帧永久漏掉，只能等收工时对最后一帧做一次深挖来兜。

现在改成：裸读没中且还一帧都没收到时，**前 3 枪就地换便宜的重试**（阈值 / 放大 / 切块）
再试一次。实测同一个场景：

```
修前：10 枪 / 1.9 秒 才拿到 1 帧
修后： 1 枪 / 0.4 秒 拿到 1 帧
```

这条对动图同样有意义：某一帧刚好糊了一点，不会再因为「画面没变」而被永久跳过。

## 六、新增：无损动图 WebP（体积约 GIF 的 1/5）

参数化调研了 [anywebp](https://github.com/itsharex/anywebp) 的思路后实测的结论：
它的 Go 实现用不上（GIF 只取首帧），但「无损 WebP」这条路对动图确实有效。

同一批帧，720px 双色：

| 产物 | 15 帧 | 57 帧 |
|---|---|---|
| GIF | 0.50 MB | 2.00 MB |
| 动图 WebP（无损 `method=4`） | **0.10 MB** | **0.39 MB** |
| 省 | **5.3×** | **5.2×** |

**逐像素无损**（不是近无损）、逐帧全可读、`unpack` 直接吃 `.webp`。
反直觉的一点：**WebP 有损反而更大** —— q90 是 415KB/15 帧，比无损大 4 倍，
因为它的有损通道是为照片设计的，用在 1-bit 图形上块效应把格子弄脏，熵反而上去。

所以只提供**无损**一档，且**默认不启用**：能播动图 WebP 的播放器比 GIF 少
（Windows「照片」、微信可能只显示第一帧）。咱们的流程是「让动图在屏幕上循环播放再框选」，
播不动就等于产物废掉 —— 所以只在显式选择时输出。

- 图形界面：格式下拉新增 `WebP 动图`（**只出** WebP）、`GIF + WebP`、`PNG + GIF + WebP`
- 命令行：`--qr-webp`；配 `--no-single --no-sheet` = 只要一张 WebP
- 顺带修：选了动图格式但文件一帧就装下时，以前会**什么都不输出**，现在回落成单帧 PNG

## 验证

- **139 项单测全绿**（新增 7 项：跨屏物理像素换算 ×2、失败留证 ×1、动图 WebP ×3、快扫失手就地重试 ×1）
- 真机双屏、125% 缩放、副屏显示真码、**走完整 GUI 路径**：

  ```
  · 屏幕缩放 125%：框选坐标已按物理像素换算
  · 正在扫描框选区域 875×875 @ (1995,100)
  · 本轮扫描：1 枪 / 0.4 秒，新收 1 帧
  ✅ 从屏幕框选识别 1 帧 → 还原 1 个文件（SHA-256 一致）
  ```

- 同一场景换回旧坐标：`抓图 700×700 → ❌ 没识别到`
- 动图 WebP：逐像素与直接渲染结果一致、`unpack` 还原后 SHA-256 与原文一致

## 升级建议

**双屏 / 屏幕缩放不是 100% 的用户请务必升级** —— 这是本版的主要修复。
单屏用户升级也无害（换算比值为 1，行为不变）。

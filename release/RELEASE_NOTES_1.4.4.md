# v1.4.4 — 一次框选收全 978 帧，不用再框十几次

## 一句话

上一版修好了「副屏框不准」，但真跑 978 帧的动图才发现根子不在识别速度：
**连拍上限写死 30 秒，而这段动图播一轮要 326 秒 —— 一轮都播不完，结构上就不可能收全**。
这一版把上限变成「按总帧数算、按实测播放速度续命」，再把每枪耗时砍掉四成，
大文件满 100% 后也不再干等 30 秒。

## 一、先回答一个问题：3 帧/秒的动图，识别真的跟不上吗？

跟不上的是**时间预算**，不是解码。实测一枪（抓图 + 指纹 + 解码 + 间隔）：

| 步骤 | v1.4.3 | 现在 |
|---|---|---|
| 抓图 | **92.6ms**（Pillow 每次把整个虚拟桌面 3840×1200 抓下来再裁） | **16.9ms**（GDI `BitBlt` 只抓框内 971×948） |
| 画面指纹 | 7.1ms | 7.1ms |
| 解码 | 37ms | 37ms |
| 枪间隔 | 50ms | 50ms |
| **一枪合计** | **~187ms → 5.3 枪/秒** | **~111ms → 9.0 枪/秒** |

**5.3 枪/秒 对 3 帧/秒 已经是 1.8 倍超采样**，本来就追得上。你日志里那
`978 帧按 3 帧/秒播一轮 = 326 秒`，而程序 30 秒就收工 —— 每轮只能拿到
30 秒 × 3 帧 = 90 帧，正好对上日志里的 `收到 90 帧 / 31.6 秒`。
978 ÷ 90 ≈ **11 轮**，还要叠加每轮播放相位不同造成的重叠，于是框了二十轮还在漏。

抓图那一步换成了 Windows GDI `BitBlt`，只抓框内那块并直接读成位图：
和 `ImageGrab` 抓的图**逐像素完全一致**（连测 3 轮全等），只是快 5.5 倍。
不是拿画质换速度。现在 9 枪/秒 → 一轮能打 2900 多枪，是 978 帧的 3 倍。

## 二、一次框选收全：上限按「够播 2.5 轮」算，收齐前不停

收到第一帧就从段头读出总帧数（`#OPK1 …/978`），把上限放宽到
`总帧数 ÷ 帧率 × 2.5 + 15` 秒 —— 978 帧按 3 帧/秒就是 **830 秒**。
小文件不受影响（取两者较大的，30 秒照旧够）。

**帧率按界面上设的「帧/秒」来匹配**：屏幕上那段 GIF 就是本程序按这个帧率生成的，
两者对得上才能算准「播一轮要多久」。拿不准也不怕 —— 还会用**实测收帧速度**再校准
一次：播放被拖到 1.5 帧/秒，就按 1.5 帧/秒 重新算，自动续命。

停止条件换成「收齐才停」：

| 情况 | 行为 |
|---|---|
| 收齐了 | 立刻停，开始还原 |
| 点了「停止」 | 立刻停，已收的帧保留 |
| 连续**两整轮**一帧新的都没有 | 停（屏幕上确实没得收了） |
| 连续 20 秒没有新帧 | 停（播放器暂停/被挡住了） |
| 到 1800 秒还没收齐 | 停（兜底，防止对着别人的动态码空转） |

以前的规则是「到 30 秒就停」—— 978 帧的动图一轮 326 秒，永远只能收到 90 帧。
现在只要还在往上涨，就一直收。

## 三、悬浮条会说「还要多久」

「这得识别到什么时候」—— 现在角落的小条直接给答案：

```
正在连拍收帧 · 别切窗口
已收 631/978 帧 · 还要 1 分 40 秒        [停止]
```

日志同步：`已收 631/978 帧（620 枪 · 已用 218 秒 · 还要 1 分 40 秒）`。
前 8 帧样本太少，显示「正在估时」而不是瞎猜。

## 四、扫描期间有悬浮条：能看进度、能停

以前框选时主窗口藏着，几分钟的扫描既看不到进度也没法中止。现在框外角落会出现一条小状态条：

- 自动躲开框选区域（免得它自己挡住要扫的码）；整屏都被框住时不显示
- 点「停止」立刻收工，已收到的帧照常保留，下次接着收

## 五、主窗口彻底藏住

用户实测：「只是最小化而不是完全隐藏，中途可以打开」。

现在扫描期间每秒检查一次，只要主窗口露头（从任务栏点回来、Alt+Tab）就立刻再藏回去 ——
它一出现就压在要扫的码上，每枪画面里都会多出一块窗口，直接毁掉识别。

## 六、「再来一轮」按钮（不用重新拖框）+ 缺帧说清楚

现场记录：为了收全 978 帧，用户**框了 35 次**。每次都要重新拖一遍框，手一抖框歪
又白扫一轮 —— 这是纯摩擦。

- 缺帧时底部出现两个按钮：
  - **再来一轮（还是那块区域，不用重框）** —— 记住上次的物理坐标，一键重扫
  - **重新框选（接着收同一份文件）** —— 只有框歪了才需要
- 缺帧从「一千多个数字」压成区间：

  ```
  共 978 帧，已收 181，缺 797 帧：第 1–118、209–547、639–978 帧
  ```

- 日志从 0.5 秒一行改成 **3 秒一行**，并直接带进度。
  以前刷六十多行，把有用的信息全冲走了。

## 七、大文件不再「100% 卡住 30 秒」

```
合成 WebP 100% (980/980) · 113s     ← 进度满格，然后干等
```

出图只是前半程；后半程是 PIL 把 980 帧一次性压进一个动图文件，**这步没法按帧报进度**。
现在会先报一个「写入 WebP」阶段，进度条切成来回滚动的动画，并提示
「大文件要几十秒，别关窗口」—— 不再看着满格进度条干瞪眼。

## 八、补上 `WebP 动图` 单出（1.4.3 漏的）

1.4.3 只有 `GIF + WebP` 和 `PNG + GIF + WebP`，没有**只出 WebP** 的选项。现在补上：

- 图形界面：下拉新增 `WebP 动图`（不出 PNG、不出 GIF）
- 命令行：`--qr-webp --no-single --no-sheet` = 只要一张 WebP
- 顺带修一个静默 bug：**选了动图格式但文件一帧就装下时，以前会什么都不输出**，
  现在回落成单帧 PNG

## 验证

- **全量单测通过**（152 项；新增：一轮收全、实测速率续命、上限天花板、ETA 估算、
  帧率跟随界面设置、再来一轮复用区域、GDI 抓图读真码、区间压缩、写入阶段上报）
- 真机实测：GDI 抓图 vs `ImageGrab` **逐像素一致**，92.6ms → 16.9ms（5.5×）
- 真机实测：单枪 187ms → 111ms（5.3 → 9.0 枪/秒）
- 单测模拟「首标识 + 数据帧 + 尾标识」循环播放，断言**一次 `scan_region` 就收全每一帧**
- 打包产物 10/10 通过

## 升级建议

**处理过上百帧动图的用户必升** —— 「30 秒上限」这个坑不修，
再框一百次也收不全（有人框了 35 次）。用法也跟着变：**框一次，让它自己跑几分钟
跑完一轮就行**，别再反复框；悬浮条上会实时告诉你还要多久。

## 构建说明（给维护者）

Windows 上正在运行的那个 exe 会锁住它所在的目录（连改名都不行），
所以打包装到了独立目录，靠 `OFFICEPACK_DIST` 指过去：

```bash
python -m PyInstaller --noconfirm --distpath dist_pkg --workpath build/gui build/OfficePack-GUI.spec
OFFICEPACK_DIST=dist_pkg python scripts/trim_dist.py
OFFICEPACK_DIST=dist_pkg python scripts/verify_release.py
OFFICEPACK_DIST=dist_pkg python scripts/make_zips.py
```

# OfficePack 1.4.9 发布说明

> 一句话：**底部进度行不再被裁**（根因是布局在处理途中长高了 28px），
> 进度条按要求缩短到 480px，文字不再被裁；同时把「3×3 到底要多大的屏」算清楚。

---

## 一、修：「合成的时候底部还是显示不全」

### 根因不是宽度，是高度在跑的过程中变了

底部那行（6px 进度条 + 一行说明文字）原来是「有活干才 pack」：

| 时刻 | 整窗需要的高度 |
|---|---|
| 空闲 | 943px |
| 一进合成阶段（进度行出现） | **970px** |

窗口此时已经贴在工作区下沿，长不高 → Tk 只能去压别人。两个表现：

1. **右侧选项区被压 27px** → 突然冒出滚动条（上一轮刚修过一次，这回是同一个根因的另一个出口）
2. **底部进度行贴着窗口下沿** → 看着就是「显示不全」

### 改法：那一行固定占位

```
self._sub_row = ttk.Frame(self._foot, height=SUB_ROW_H=24)
self._sub_row.pack(fill="x", padx=8, pady=(0, 2))
self._sub_row.pack_propagate(False)      # 高度写死，子控件不再把它撑开
```

空闲时只是空白（行在、条子和文字藏起来），从启动到收尾整窗 `reqheight` **一点不变**。
顺带把日志的下边距并进这行，净代价只有一行日志。

实测（1920×1200@125%）：

| | 空闲 | 合成阶段 |
|---|---|---|
| 整窗需要高度 | 962px | **962px**（不变） |
| 选项区画布高度 | 545px | **545px**（不再被压，无滚动条） |
| 日志行数 | 14 | 14 |

## 二、改：进度条缩短，文字不再被裁

- 进度条封顶 **480px**（原来铺满剩余空间 690px），右边余量全给文字
- 文字不再用 `width=31` —— 这个参数的单位是**字符数**，阶段名一长，
  末尾的「100% (3825/3825)」就被硬裁掉，而那正是最该看到的数字

现在：文字按内容自适应，超长（>42 字符）自己加省略号；窗口拉伸时进度条跟着重算长度，
永远是「文字优先、条子占剩下的、封顶 480」。

## 三、答：3×3 到底要多大屏？

**矩阵是正方形，卡的是屏幕高度，不是宽度。** 单码按 720px 生成，3×3 拼出来
**2244×2244**（含 12px 缝），要 1:1 不缩放显示，屏幕上就得有一块 2244×2244 的可视区域：

| 分辨率 | 工作区高 | 每张码 | 像素/模块 | 结论 |
|---|---|---|---|---|
| 1920×1080（任务栏占 40） | 1040 | 347px | 2.0 | 勉强，且极易被切边 |
| 1920×1200 | 1130 | 377px | 2.1 | 勉强 |
| 2560×1440 | 1360 | 453px | 2.6 | 可用 |
| 3840×2160 | 2080 | 693px | 3.9 | 舒适（接近原图） |

实测解码下限（400KB 文件、version 40 的码，按比例缩到各尺寸）：

| 每张码 | 像素/模块 | 结果 |
|---|---|---|
| 720px | 4.1 | 36/36 |
| 420px | 2.4 | 36/36 |
| 350px | 2.0 | 27/27（走整图识别） |
| 300px | 1.7 | 26/27，开始掉 |

**为什么一般显示器「看着能播、却总收不全」？** 两个原因叠在一起：

1. 被压小 —— 1080p 的工作区只有 1040 高，2244 的正方形只能缩到 46%
2. **只要被切掉一条边，就是整整一行码丢失** —— 任务栏、窗口标题栏、播放器边距、
   看图软件的白边，任何一个都能造成「每枪只认出 6/9」

所以：**1080p / 笔记本优先 2×2**（每码 520px，2.9 像素/模块，正好够）；
1440p 以上再上 3×3；3×3 的舒适区是 4K。要 3×3 就用浏览器 F11 全屏、确认整个正方形
都露出来。

「开始处理」时程序会把这两笔账直接打给你看，像素不够会给出替代建议。

## 四、补录（「再来一轮」）不再 3 秒就放弃

实测日志里最扎眼的一段：

```
· 本轮扫描：45 枪 / 3.2 秒 / 0 轮，新收 0 帧（累计 3811 帧）
· 实测收帧 0.0 帧/秒（设定 10）：播放器跟不上，改小帧率或换个播放器
```

**这不是播放器跟不上。** 是判死规则用错了场景：

- 第一轮：画面从首帧开始播，3 秒内一定见到 `#OPKmark|S`，之后靠「连续两轮没有新帧」收工
- 补录：画面可能正播在中段，等首帧标识要等**半圈**（3823 帧的动图一圈 1 分钟以上）
  → 3 秒判死，等于一点机会都不给

改法：续扫时判死时间按「够播一整轮」算（`400 帧 ÷ 帧率 + 10 秒`，上限 240 秒），
所以补 12 帧真的会跑完整一圈才收工。顺带把提示改准：一帧没补到时会说
「这轮没转到缺的那几帧，再点一次」，不再误导用户去调帧率、换播放器。

## 五、采样抖动：从「随机抖」换成「按缺口算相位」

3823 帧里固定缺 340–343、844–847、3820–3823 —— 补几轮都是这几段，**典型的采样
相位卡死**：播放周期和采样周期一成整比，每轮都会稳定地跨过同几个时间点。

原来的做法是每次采样之间加 ±25% 随机抖动。随机能用，但**靠运气** —— 收齐 N 帧
的期望次数是 N·lnN 量级，帧数越多越难凑（这就是「帧数越多越难以收录」）。

现在换成确定性算法，三件事：

### 1）步长才是主因

`step = 播放帧率 ÷ 采样帧率`（两枪之间画面往前走了几帧）。

| step | 一轮最多收到 | 说明 |
|---|---|---|
| ≤ 1 | 100% | 枪速≥播放率，一轮就该齐，抖动不重要 |
| ≈ 1 | ~100% | 最常见（播放器 10 帧/秒、程序 10 枪/秒），缺的那几帧是解码失手 |
| 2 | 50% | 只能落在一半的相位上 |
| 3 | 33% | 每轮都漏同样两帧，补几轮都一样 |

**step > 1 时，再高明的抖动也只是把漏的换一批**，真正省时间的是把枪速提上去。

### 2）每轮往后挪多少：二分序列

采样以「见到首帧标识 `S` 的那一枪」为相位 0 点（之前完全没有参照物，挪了也白挪），
每一圈把采样网格整体平移：

```
0 → 1/2 → 1/4 → 3/4 → 1/8 → 5/8 → 3/8 → 7/8 …
```

这就是 van der Corput（二进制倒序）序列，每一项都落在**现存最大空隙的正中间**，
把最宽的那段缺口对半劈开。所以 R 圈之后最大缺口缩到 `1/2^R` 齿 —— 确定性的，
不是抽签。

配套还加了一条：**每圈采样周期抖 ±2%**。步长不是整数时（如 3.33），采样点会卡在
「10 帧一轮、3 枪一循环」的**格点**上，残留那两帧永远落不到格子 —— 实测补 5 轮都
停在 22/24。周期漂一点，格子才会碾过所有相位（实测同一场景第 4 轮就齐了）。

### 3）一共要几轮：模拟到收齐，同时比总耗时

`qr.plan_jitter()` 拿已收帧的**环形缺口**（首尾相接，跨环也算）当输入，把一齿切成
24 份逐份模拟「挪到这里能多收多少帧」，取收益最大的一份，一直模拟到收齐 ——
于是同时得到「下一轮挪多少」和「还要几轮」。

实测（24 帧样本，`should_stop` 4 秒掐断模拟「一轮收不完」）：

| 播放/采样 | 第 1 轮 | 预测 | 实际 |
|---|---|---|---|
| 10 / 5 帧/秒 | 18/24（step 2.07） | 再 1 轮 | 第 2 轮 24/24，**对上** |
| 10 / 3 帧/秒 | 9/24（step 3.04） | 再 3 轮 | 第 2→3→4 轮 24/24，**正好 3 轮** |

## 六、最快路线：比的是总耗时，不是轮数最少

用户要求「最快、性能最佳」，所以规划器的目标函数是**秒**：

- 补轮路线：每一轮都得让动图走完一整圈，耗时 ≈ 轮数 × 一圈时长
- 提枪速路线：枪速 > 播放率时一轮之内就能扫完，耗时 ≈ 一圈

轮数 ≥ 2 时提枪速必然更快，程序直接给数字：

```
步长 3.33（采样比播放慢），补轮要 3 轮 ≈ 7 秒；
最快是把「动图帧率」提到 12 帧/秒，一轮 ≈ 2 秒就齐，快 2.9 倍
```

而且补录时**自动**把帧率调到那个值（只升不降、上限 20），日志里写清改了什么：

```
· 已把「动图帧率」3 → 12（枪速超过播放率）：一轮就能扫完，比按原设置补 3 轮快
```

只要一轮就够时（step ≤ 1）反而 **不动**用户设置 —— 那时再提帧率不会更快。

## 七、「框选屏幕区域」现在等于重新开始；另有「放弃本次识别」

用户实测发现一个**会串文件**的问题：点「还原二维码 → 框选屏幕区域」想重新框一份
新文件，工具却「接着上次」，把老文件攒的帧一起拼进去 —— 那天老文件碰巧已经齐了
才没出事。

现在语义分清楚：

| 入口 | 行为 |
|---|---|
| 还原二维码 → 框选屏幕区域 | **从零开始**：上一次攒的帧作废，临时抓图一起删 |
| 再来一轮（只补 N 帧） | 续扫：同一块区域，只补缺的帧，已收的不重收 |
| 重新框选（只补 N 帧） | 续扫：换一块区域，接着收同一份文件 |
| 放弃本次识别（清掉已收的帧） | 清空攒的帧 + `%TEMP%` 抓图，下次从零开始 |

这三个按钮**并排一行**（原来各占一行要 96px，实测把日志从 14 行压到 8 行）；
并排只花 32px，日志一行都不少。

「放弃」有二次确认，手滑点了不会把几千帧弄丢。

## 八、悬浮条：宽度自适应 + 透明度不再「弹出窗口」

- **宽度不足**：原来是写死的 440px，「已收 3803/3823 帧（本轮 +3803）· 还要 1 分钟」
  直接被裁掉尾巴。现在按最长可能出现的文字量一次宽度（只增不减，免得抖动），
  上限是虚拟桌面宽 - 40。
- **调透明度时窗口乱跑**：拖动事件原来绑在 Toplevel 上，而 Tk 的 bindtags 里
  Toplevel 是每个子控件的祖先标签 —— 按滑杆等于同时在拖窗口。现在只绑标题/状态/
  空白背景，滑杆和按钮各干各的。
